# ファイル分けを行う理由

このドキュメントは、`yorimichiBiyori` でなぜファイル分けを行うのかを説明するためのものです。

ファイル分けは、単に「きれいに見せるため」の作業ではありません。  
実装が進んだあとに、コードを探しやすくし、直しやすくし、壊しにくくするための設計です。

---

## 結論

ファイル分けを行う理由は、次の4つです。

1. どこに何があるか分かりやすくするため
2. 1つのファイルが大きくなりすぎるのを防ぐため
3. 変更したときの影響範囲を小さくするため
4. AI agent やチームメンバーが迷わず作業できるようにするため

特に `yorimichiBiyori` では、画面、行動データ、提案ロジック、履歴保存、共通 UI を分けておくことが重要です。

---

## ファイル分けを行わない世界線

まず、ファイル分けをしない場合を想像します。

例えば、`App.tsx` だけにすべてを書くとします。

```text
src/
├─ App.tsx
├─ main.tsx
└─ index.css
```

最初はこれでも動きます。

ホーム画面だけなら、`App.tsx` に入力フォームを書けば済みます。  
提案ボタンも、条件の state も、仮の行動データも、同じファイルに書けます。

しかし、機能が増えると `App.tsx` は次のようになります。

```tsx
function App() {
  // 空き時間の state
  // 強度の state
  // 場所の state
  // 予算の state
  // 行動データの配列
  // 条件に合う行動を絞り込む処理
  // ランダムに1件選ぶ処理
  // 実施履歴の state
  // localStorage から履歴を読む処理
  // localStorage に履歴を書く処理
  // 実施率を計算する処理
  // ホーム画面の JSX
  // 提案画面の JSX
  // 履歴画面の JSX
  // 設定画面の JSX
  // 履歴削除処理
  // エラー表示
  // 空状態表示
}
```

この状態になると、1つのファイルが何百行にもなります。

そして、次のような問題が出ます。

---

## 問題1: どこを直せばいいか分からなくなる

例えば、「履歴表示の見た目を少し変えたい」と思ったとします。

ファイル分けされていない場合、`App.tsx` の中から履歴表示の JSX を探す必要があります。

しかし、同じファイルの中には次のものも混ざっています。

- ホーム画面
- 提案画面
- 設定画面
- 行動候補データ
- 提案ロジック
- localStorage 処理
- 実施率計算

つまり、履歴画面を直したいだけなのに、関係ないコードの中を探し回ることになります。

ファイル分けされていれば、まず `src/pages/HistoryPage.tsx` を見ればよいと分かります。

---

## 問題2: 変更の影響範囲が大きくなる

1つのファイルに多くの処理が集まっていると、小さな変更でも他の処理に影響しやすくなります。

例えば、提案ロジックを少し変えたいだけなのに、同じファイル内で履歴保存や画面表示の state も触ってしまう可能性があります。

ファイル分けされていない場合:

```text
App.tsx
├─ 入力フォーム
├─ 提案ロジック
├─ 履歴保存
├─ 履歴表示
└─ 設定画面
```

提案ロジックを変更するつもりが、履歴表示の変数名と衝突したり、不要な再レンダリングを増やしたりすることがあります。

ファイル分けされている場合:

```text
src/features/recommendation/
└─ recommendation.ts
```

提案ロジックだけを確認すればよくなります。

---

## 問題3: 同じ処理を何度も書きやすくなる

ファイル分けをしていないと、「前に書いた処理がどこにあるか分からない」状態になりやすいです。

その結果、似たような処理を別の場所にもう一度書いてしまいます。

例えば、履歴を localStorage から読む処理を、履歴画面と設定画面でそれぞれ書くかもしれません。

```ts
const records = JSON.parse(localStorage.getItem("yorimichi-biyori-records") || "[]");
```

これを複数箇所に直接書くと、保存キーを変更したいときにすべて修正する必要があります。  
1箇所でも修正漏れがあると、画面によって違うデータを読みに行く可能性があります。

ファイル分けしていれば、次のようにできます。

```text
src/features/records/
└─ recordStorage.ts
```

```ts
export function loadRecords() {
  // localStorage から履歴を安全に読む
}
```

履歴を読みたい画面は、この関数を使えばよくなります。

---

## 問題4: AI agent が迷いやすくなる

AI agent に作業を依頼する場合、ファイル分けは特に重要です。

ファイル構成が整理されていないと、AI agent は次のような判断をしづらくなります。

- 新しい処理をどこに追加するべきか
- 既存の処理をどこから探すべきか
- どの変更が画面に関係するのか
- どの変更がロジックに関係するのか
- どのファイルを触ると影響が大きいのか

その結果、AI agent が `App.tsx` にどんどん処理を追加してしまうことがあります。

これは短期的には動くかもしれません。  
しかし、後から読む人間にとっては、どこから手を付ければよいか分からないコードになります。

ファイル分けをしておくと、AI agent にも次のように指示しやすくなります。

```text
提案ロジックは src/features/recommendation/ に置く。
履歴保存処理は src/features/records/ に置く。
画面コンポーネントは src/pages/ に置く。
共通 UI は src/components/ に置く。
```

これは AI agent にとっても、人間にとっても分かりやすいルールです。

---

## 問題5: コードレビューがしにくくなる

ファイル分けをしていないと、1つの Pull Request で巨大な `App.tsx` が変更されることになります。

レビューする側は、次のような内容を一度に確認しなければいけません。

- UI の変更
- 提案条件の変更
- localStorage の変更
- 型の変更
- 履歴表示の変更
- 実施率計算の変更

これでは、どの変更が本当に必要なのか分かりにくくなります。

ファイル分けされている場合、変更ファイルを見るだけで意図が分かりやすくなります。

```text
src/pages/HistoryPage.tsx
src/features/records/recordStorage.ts
src/types/record.ts
```

この変更であれば、「履歴まわりの変更だ」とすぐに分かります。

---

## ファイル分けを行う世界線

ファイル分けを行う場合、`yorimichiBiyori` では次のような構成を目指します。

```text
src/
├─ app/
│  └─ router.tsx
├─ components/
│  ├─ layout/
│  └─ ui/
├─ data/
│  └─ activities.json
├─ features/
│  ├─ activities/
│  ├─ recommendation/
│  └─ records/
├─ pages/
│  ├─ HomePage.tsx
│  ├─ SuggestPage.tsx
│  ├─ HistoryPage.tsx
│  └─ SettingsPage.tsx
├─ types/
├─ utils/
├─ App.tsx
└─ main.tsx
```

この構成では、ファイルの役割が分かれます。

| 場所 | 役割 |
|---|---|
| `src/pages/` | 画面そのもの |
| `src/components/` | 複数画面で使う UI 部品 |
| `src/features/` | 機能単位の処理 |
| `src/data/` | 静的データ |
| `src/types/` | 共通の型 |
| `src/utils/` | 汎用関数 |
| `src/app/` | アプリ全体の設定 |

このように分けることで、「何をどこに書くか」が明確になります。

## yorimichiBiyori での具体例

### ホーム画面

ホーム画面は、空き時間・強度・場所・予算を入力する画面です。

置き場所:

```text
src/pages/HomePage.tsx
```

ここには、画面全体の構成を書きます。

ただし、ボタンや入力欄など、他の画面でも使う部品は `src/components/` に分けます。

---

### 提案ロジック

条件に合う行動を探す処理は、画面表示そのものではありません。

置き場所の例:

```text
src/features/recommendation/recommendation.ts
```

このファイルには、例えば次のような関数を置きます。

```ts
export function filterActivities(activities: Activity[], condition: SuggestionCondition) {
  return activities.filter((activity) => {
    return activity.durationMinutes <= condition.availableMinutes
      && activity.budgetYen <= condition.budgetYen;
  });
}
```

こうしておくと、提案画面以外からも同じロジックを使えます。

---

### 履歴保存

localStorage への保存や読み込みは、画面に直接書かないほうがよいです。

置き場所の例:

```text
src/features/records/recordStorage.ts
```

このファイルに次のような関数を置きます。

```ts
export function loadRecords(): ActivityRecord[] {
  // localStorage から履歴を安全に読み込む
}

export function saveRecords(records: ActivityRecord[]) {
  // localStorage に履歴を保存する
}
```

こうすると、履歴画面でも設定画面でも同じ処理を使えます。

---

### 型定義

行動データや履歴データの型は、複数のファイルから使われます。

置き場所の例:

```text
src/types/activity.ts
src/types/record.ts
```

型を共通化しておくと、データ構造を変更したときに影響範囲が分かりやすくなります。

---

## App.tsx に何を書くのか

ファイル分けを行う場合、`App.tsx` はできるだけ薄くします。

`App.tsx` の役割は、アプリ全体の土台を組み立てることです。

例えば、次のような役割に留めます。

- ルーターを表示する
- 全体レイアウトを適用する
- アプリ全体に必要な provider を置く

逆に、以下は `App.tsx` に詰め込みすぎないほうがよいです。

- 行動候補の配列
- 提案ロジック
- localStorage の読み書き
- 履歴一覧の JSX
- 各画面の細かい UI

`App.tsx` が薄い状態を保てていると、アプリ全体の見通しがよくなります。

---

## ファイル分けしすぎにも注意する

ファイル分けは重要ですが、分ければ分けるほどよいわけではありません。

例えば、まだ数行しかない処理を無理に1ファイルに分けると、逆に追いにくくなります。

避けたい例:

```text
src/utils/getOne.ts
src/utils/getTwo.ts
src/utils/isEmptyString.ts
src/utils/formatOneWord.ts
```

このように細かすぎる分割をすると、ファイルを開く手間が増えます。

基本方針は次の通りです。

1. まずは同じ責務のコードを近くに置く
2. ファイルが大きくなったら分ける
3. 複数箇所で使うようになったら共通化する
4. 分けたほうが名前を付けやすいときに分ける

「分けること」自体が目的ではありません。  
読みやすく、探しやすく、変更しやすくすることが目的です。

---

## 判断基準

ファイルを分けるか迷ったら、次の質問を使います。

### 1. その処理は画面表示ですか？

画面そのものなら `src/pages/`、再利用する UI 部品なら `src/components/` に置きます。

### 2. その処理は機能のロジックですか？

提案、履歴、行動データの加工などは `src/features/` に置きます。

### 3. 複数の場所で使いますか？

複数箇所で使う型は `src/types/`、汎用関数は `src/utils/` に置きます。

### 4. データそのものですか？

行動候補のような静的データは `src/data/` に置きます。

### 5. アプリ全体の設定ですか？

ルーティングなどは `src/app/` に置きます。

---

## まとめ

ファイル分けをしない世界線では、最初は楽です。

しかし、機能が増えるほど次の問題が起きます。

- どこを直せばいいか分からない
- 変更の影響範囲が大きい
- 同じ処理を何度も書く
- AI agent が迷う
- コードレビューがしにくい
- `App.tsx` が巨大化する

ファイル分けを行うと、次の状態を作れます。

- 画面は `src/pages/`
- 共通 UI は `src/components/`
- 機能ロジックは `src/features/`
- 静的データは `src/data/`
- 共通型は `src/types/`
- 汎用関数は `src/utils/`
- アプリ設定は `src/app/`

つまり、ファイル分けは「整理整頓」ではなく、開発を続けるための安全装置です。
