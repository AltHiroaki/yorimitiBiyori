# コーディング規則の考え方

このドキュメントは、開発者が `yorimichiBiyori` のコーディング規則を理解するための説明です。

AI agent に直接読ませる規則は、以下の2つにまとめています。

- [General Coding Skill](./SKILL.md)
- [AI Agent Rules for yorimichiBiyori](./AGENTS.md)

このファイルでは、規則そのものだけでなく「なぜそうするのか」を説明します。

---

## なぜ AI 向けの規則を英語にするのか

AI agent に渡す指示は、英語のほうが安定しやすいです。

理由は、コーディング規約、公式ドキュメント、OSS の README、Issue、Pull Request など、プログラミングに関する情報の多くが英語で書かれているためです。

例えば、次のような表現は AI agent にとって解釈しやすいです。

```md
Prioritize readability.
Avoid magic numbers.
Separate UI logic from business logic.
Do not add advanced features before the MVP is stable.
```

一方で、開発者が理由や背景を理解するには日本語のほうが読みやすい場合があります。  
そのため、このリポジトリでは次のように役割を分けます。

| ファイル | 言語 | 目的 |
|---|---|---|
| `docs/SKILL.md` | 英語 | AI agent に読ませる汎用コーディング規則 |
| `docs/AGENTS.md` | 英語 | AI agent に読ませるプロジェクト固有規則 |
| `docs/coding-rules-guide.md` | 日本語 | 開発者が規則の理由を理解するための説明 |

## 可読性を最優先する理由

コードは、書く時間よりも読む時間のほうが長くなります。

特にチーム開発では、自分が書いたコードを他のメンバーが読むことがあります。さらに、数日後や数週間後の自分も「他人に近い状態」でコードを読むことになります。

そのため、短く書くことよりも、意図が分かることを優先します。

避けたい例:

```ts
const r = activities.filter((x) => x.t <= m && x.b <= p).sort(() => Math.random() - 0.5)[0];
```

このコードは短いですが、`r`, `x`, `t`, `m`, `b`, `p` が何を意味するのか分かりにくいです。

望ましい例:

```ts
const matchedActivities = activities.filter((activity) => {
  return activity.durationMinutes <= availableMinutes
    && activity.budgetYen <= selectedBudgetYen;
});

const suggestedActivity = getRandomActivity(matchedActivities);
```

行数は増えますが、何をしているかが読みやすくなります。

## マジックナンバーを避ける理由

マジックナンバーとは、意味の説明がないままコード中に直接書かれた数値です。

避けたい例:

```ts
if (availableMinutes >= 15) {
  // ...
}
```

この `15` が何を意味するのか、コードだけでは分かりません。

望ましい例:

```ts
const MIN_ACTIVITY_MINUTES = 15;

if (availableMinutes >= MIN_ACTIVITY_MINUTES) {
  // ...
}
```

定数名を付けることで、「この値は最短の活動時間を表している」と分かります。

ただし、すべての数値を定数にする必要はありません。  
例えば、配列の先頭を表す `0` や、パーセンテージ計算の `100` は意味が明確なので、そのまま使っても構いません。

---

## 命名を具体的にする理由

曖昧な名前は、読み手に推測を強制します。

避けたい名前:

```ts
const data = getData();
const result = data.filter((item) => item.flag);
```

このコードでは、何のデータで、何の結果で、何を表すフラグなのか分かりません。

望ましい名前:

```ts
const activities = getActivities();
const matchedActivities = activities.filter((activity) => activity.isAvailable);
```

名前を具体的にするだけで、コメントがなくても処理の意味が伝わりやすくなります。

## 関数の責務を分ける理由

1つの関数に複数の責務を詰め込むと、修正時の影響範囲が分かりにくくなります。

避けたい例:

```ts
function suggestAndSaveActivity() {
  // 条件を取得する
  // 行動候補を絞り込む
  // ランダムに選ぶ
  // 履歴に保存する
  // 画面状態を更新する
}
```

この関数は多くのことをやりすぎています。  
どこか1つを変更したいだけでも、他の処理に影響する可能性があります。

望ましい分け方:

```ts
const matchedActivities = filterActivities(activities, condition);
const suggestedActivity = getRandomActivity(matchedActivities);
saveActivityRecord(suggestedActivity);
```

処理を分けることで、それぞれの関数の目的が明確になります。

---

## UI とロジックを分ける理由

React コンポーネントにすべての処理を書くと、画面表示とアプリのロジックが混ざります。

混ざりやすい処理の例:

- 行動候補の絞り込み
- ランダム提案
- 実施率の計算
- localStorage の読み書き
- 日付表示の整形

これらをページコンポーネントに直接書きすぎると、画面が大きくなり、修正しづらくなります。

例えば、提案ロジックは以下のように分けると扱いやすくなります。

```ts
const matchedActivities = filterActivities(activities, condition);
const suggestedActivity = getRandomActivity(matchedActivities);
```

画面側は「何を表示するか」に集中し、ロジック側は「どう計算するか」に集中できます。

## yorimichiBiyori のプロダクト目標

`yorimichiBiyori` は、短い空き時間にできる小さな行動を提案するアプリです。

提案に使う主な条件は以下です。

- 空き時間
- 強度
- 場所
- 予算

主な利用者は、授業・アルバイト・サークル活動の間に 15〜60 分程度の空き時間が生まれる大学生です。

この前提を明確にしておく理由は、実装判断がぶれないようにするためです。  
例えば、社会人向けの長期タスク管理機能や、旅行アプリのような本格的なスポット検索機能は、現時点の中心目的から外れます。

まずは「今ある短い空き時間をどう使うか」に集中します。

---

## MVP を優先する理由

`yorimichiBiyori` では、まず授業内で完成できる範囲の MVP を作ることを優先します。

Google ログイン、Google Calendar API、Firebase、Google Maps API、位置情報取得などは便利ですが、初期段階では実装難度が上がります。  
これらを早く入れすぎると、中心機能である「条件入力 → 行動提案 → 履歴保存」が完成しない可能性があります。

そのため、MVP では次の流れを安定させることを優先します。

```text
条件入力 → 行動提案 → 実施 / スキップ記録 → 履歴表示 → 実施率表示
```

発展機能は、MVP が動いてから追加します。

### MVP に含める機能

MVP では、以下に集中します。

- 空き時間の手動入力
- 強度の選択
- 場所の選択
- 予算の選択
- 条件に合う行動提案
- 別の提案の再表示
- 実施記録
- スキップ記録
- 履歴表示
- 実施率の表示

これらは、このアプリの価値を最小構成で成立させるために必要な機能です。

### MVP 完成前に入れない機能

MVP 完成前は、以下を原則として実装しません。

- Google ログイン
- Google Calendar API
- Firebase Authentication
- Firestore
- Google Maps API
- Places API
- 位置情報取得
- カレンダー予定からの空き時間自動検出
- ユーザーごとのクラウド保存
- アカウント同期

これらは便利ですが、中心機能の完成を遅らせる可能性があります。

## 技術スタックを固定する理由

このプロジェクトでは、次の技術を基本として使います。

- React
- TypeScript
- Vite
- Tailwind CSS
- React Router
- localStorage
- JSON データ

技術スタックを固定する理由は、実装方針を安定させるためです。

AI agent は、便利そうなライブラリや別の状態管理手法を提案・導入することがあります。  
しかし、MVP 段階では技術を増やすほど、学習コストやトラブル対応が増えます。

まずは、現在の構成で作れる範囲を作り切ることを優先します。

## ディレクトリ責務を決める理由

ファイルの置き場所が曖昧だと、実装が進むほどコードが探しにくくなります。

このプロジェクトでは、次の責務で分けます。

| ディレクトリ | 役割 |
|---|---|
| `src/app/` | ルーティングやアプリ全体の設定 |
| `src/pages/` | 画面単位のコンポーネント |
| `src/components/` | 再利用可能な UI コンポーネント |
| `src/features/` | 機能単位のロジックやコンポーネント |
| `src/data/` | 静的データ |
| `src/types/` | 共通 TypeScript 型 |
| `src/utils/` | 汎用関数 |

例えば、提案画面そのものは `src/pages/SuggestPage.tsx` に置きます。  
一方で、行動候補を絞り込む関数は `src/features/recommendation/` や `src/utils/` に分けたほうが読みやすくなります。

大きなディレクトリ変更を避ける理由は、README や docs の説明と実装がずれるのを防ぐためです。

---

## TypeScript の型を明示する理由

TypeScript の型は、データ構造のミスを早い段階で見つけるために使います。

このアプリでは、特に以下のデータに型を付ける必要があります。

- 行動データ
- 提案条件
- 実施・スキップ履歴

代表的な型の例です。

```ts
type Intensity = "low" | "medium" | "high";

type Activity = {
  id: string;
  title: string;
  description: string;
  durationMinutes: number;
  intensity: Intensity;
  location: string;
  budgetYen: number;
};

type ActivityRecord = {
  id: string;
  activityId: string;
  status: "done" | "skipped";
  createdAt: string;
};
```

このように型を定義しておくと、存在しないプロパティを使ったり、`done` / `skipped` 以外の状態を保存したりするミスを減らせます。

ただし、実際の型は `activities.json` の構造に合わせる必要があります。  
JSON の構造を変えた場合は、TypeScript の型も更新します。

---

## React コンポーネントの責務を分ける理由

React では、画面をコンポーネント単位で組み立てます。

このプロジェクトでは、ページコンポーネントは画面全体の構成を担当し、再利用できる UI は `src/components/` に分離します。

例えば、複数の画面で同じ見た目のボタンやカードを使うなら、共通コンポーネントにしたほうがよいです。

```text
src/components/ui/Button.tsx
src/components/ui/Card.tsx
```

同じ UI を毎回コピーすると、見た目を変更したいときに複数箇所を直す必要があります。  
共通化しておくことで、UI の統一感も保ちやすくなります。

---

## 行動データを activities.json で管理する理由

MVP では、行動候補を `src/data/activities.json` にまとめます。

理由は、データとロジックを分けるためです。

行動候補をコンポーネント内に直接書くと、画面のコードが長くなり、データの追加や修正がしにくくなります。

望ましい考え方:

```text
activities.json      行動候補の一覧
Activity 型          行動データの構造
提案ロジック          条件に合う行動を選ぶ処理
React コンポーネント   選ばれた行動を表示する画面
```

行動データを編集するときは、以下に注意します。

- 各行動に一意で安定した `id` を持たせる
- タイトルは短く分かりやすくする
- 説明文はユーザーが行動をイメージできる内容にする
- 絞り込みに必要な項目を欠かさない
- JSON の構造を変えたら TypeScript 型も更新する

---

## 提案ロジックを単純に保つ理由

提案ロジックでは、基本的に以下の条件を使います。

- 空き時間
- 強度
- 場所
- 予算

最初から複雑な推薦アルゴリズムを作る必要はありません。

MVP では、まず次の処理が動くことを優先します。

```text
activities.json から読み込む
↓
条件に合う行動だけに絞る
↓
候補の中から1つ提案する
↓
候補がない場合の表示を出す
```

同じ提案を連続で出さない工夫などは、基本機能が安定してからで十分です。

初期実装で複雑にしすぎると、バグが出たときに原因を追いにくくなります。

## localStorage を使う理由

MVP ではログイン機能やクラウド保存を使わないため、履歴は `localStorage` に保存します。

これにより、Firebase や認証機能を実装しなくても、ブラウザ内に履歴を残せます。

ただし、`localStorage` には注意点があります。

- ユーザーがブラウザデータを消すと履歴も消える
- 別の端末とは共有されない
- `JSON.parse` に失敗する可能性がある
- 保存データの形式を変えると古いデータと合わなくなる可能性がある

そのため、読み書き処理は専用関数に分け、安全に扱う必要があります。

保存キーは定数にします。

```ts
const STORAGE_KEY = "yorimichi-biyori-records";
```

直接あちこちに文字列を書くと、キーを変更したいときに修正漏れが起きます。

---

## 実施率の計算方法を決めておく理由

実施率は、定義が曖昧だと画面ごとに計算結果がずれる可能性があります。

このプロジェクトでは、基本的に次の定義で考えます。

```text
実施率 = done の数 / (done の数 + skipped の数)
```

例えば、実施が 3 件、スキップが 1 件なら、実施率は 75% です。

履歴が 0 件の場合は、ゼロ除算が起きないようにします。  
表示は `0%` または「まだ記録がありません」のような空状態メッセージにします。

---

## Tailwind CSS の使い方を決める理由

Tailwind CSS は素早く UI を作れる一方で、クラス名が長くなりやすいです。

同じ見た目のボタンやカードを毎回直接書くと、画面ごとに微妙にデザインがずれます。

そのため、よく使う UI は共通コンポーネントにします。

```text
src/components/ui/Button.tsx
src/components/ui/Card.tsx
```

また、このアプリは短い空き時間に使う想定なので、スマートフォン表示を優先します。  
授業の合間や移動中でも、すぐ条件を入力して提案を見られる UI が望ましいです。

---

## ルーティングを app/router.tsx にまとめる理由

画面遷移の設定が複数ファイルに散らばると、どの URL がどの画面に対応しているか分かりにくくなります。

そのため、ルーティング設定は `src/app/router.tsx` にまとめます。

基本ルートは以下です。

```text
/
/suggest
/history
/settings
```

ページコンポーネントは `src/pages/` に置きます。

この形にしておくと、画面追加やパス変更が必要になったときに確認しやすくなります。

## ビルド確認を行う理由

コードを変更した後は、可能な限り以下を実行します。

```bash
npm run build
```

このコマンドにより、TypeScript の型チェックと Vite のビルド確認ができます。

画面上では一見動いているように見えても、型エラーやビルドエラーが残っている場合があります。  
ビルド確認を習慣にすると、壊れた状態で変更を終えるリスクを減らせます。

ローカルで確認できない場合は、「未確認」と明示します。

---

## 外部ライブラリを勝手に追加しない理由

外部ライブラリを追加すると、一見便利になりますが、管理するものも増えます。

- 依存関係が増える
- バージョン管理が必要になる
- ビルドサイズが増える可能性がある
- 使い方をチーム全員が理解する必要がある
- 将来の更新や互換性対応が必要になる

小さな処理であれば、TypeScript、React、ブラウザ標準 API で十分な場合が多いです。

そのため、新しいライブラリは「本当に必要な場合だけ」追加します。

---

## コメントには「なぜ」を書く理由

コードを読めば分かる内容をコメントしても、あまり役に立ちません。

避けたい例:

```ts
// records を保存する
localStorage.setItem(STORAGE_KEY, JSON.stringify(records));
```

このコメントは、コードを読めば分かる内容を繰り返しているだけです。

望ましい例:

```ts
// MVP ではログイン機能を使わないため、履歴はブラウザ内だけに保存する。
localStorage.setItem(STORAGE_KEY, JSON.stringify(records));
```

このコメントは「なぜ localStorage なのか」を説明しています。  
後から読んだ人が設計意図を理解しやすくなります。

---

## 過度な抽象化を避ける理由

共通化は重要ですが、早すぎる共通化は逆に読みにくくなることがあります。

まだ1箇所でしか使っていない処理を無理に汎用化すると、実際には不要な引数や分岐が増えることがあります。

基本方針は次の通りです。

1. まずは素直に書く
2. 同じ処理が複数回出てきたら共通化を検討する
3. 共通化するときは、名前と責務を明確にする

「重複を避けること」よりも「読みやすく保つこと」を優先します。

---

## 禁止事項を明文化する理由

AI agent は、指示されていない改善を自律的に行うことがあります。

そのため、「やること」だけでなく「やらないこと」も明文化します。

このプロジェクトでは、特に以下を避けます。

- 指示なしに外部依存を追加する
- MVP 範囲外の機能を実装する
- Google API、Firebase、Maps API、位置情報取得を追加する
- 大きなディレクトリ変更を行う
- `any` を広く使う
- UI とビジネスロジックを強く混在させる
- README や docs と矛盾する変更を行う
- 関係ないリファクタリングを混ぜる
- 動いているコードを理由なく大きく書き換える

禁止事項は、開発の自由を奪うためではなく、MVP 完成までの実装を安定させるためにあります。

---

## 判断に迷ったときの優先順位

実装中に迷った場合は、以下の順番で判断します。

1. README と docs に書かれた仕様を守る
2. MVP 完成に近づく変更を優先する
3. 可読性と保守性を優先する
4. 実装を複雑にしすぎない
5. 発展機能は後回しにする

この優先順位を決めておくと、AI agent と開発者の判断がそろいやすくなります。

例えば、「Google Calendar 連携を入れれば便利そう」と思っても、MVP が未完成なら後回しにします。  
逆に、提案ロジックや履歴保存のように MVP の中心機能に関わるものは優先します。

## 開発時の使い方

AI agent に作業を依頼するときは、必要に応じて次のファイルを渡します。

```text
docs/SKILL.md
docs/AGENTS.md
```

開発者がルールの理由を確認したいときは、このファイルを読みます。

```text
docs/coding-rules-guide.md
```

AI にそのまま指示したい場合は、`docs/SKILL.md` または `docs/AGENTS.md` のコードブロック部分をコピーして使います。

開発者が背景を確認したい場合は、このファイルで「なぜそのルールがあるのか」を確認します。
