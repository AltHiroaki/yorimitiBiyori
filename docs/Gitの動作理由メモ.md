# Gitの動作理由メモ

このファイルは、docs/Git使い方メモ.mdに書いた手順が「なぜその挙動になるのか」を短く説明するための補足です。

## 1. Gitが管理している3つの場所

Gitの理解は、次の3つを分けて考えると整理しやすいです。

1. ワーキングツリー
- 実際に編集しているファイルの場所。

2. インデックス（ステージ）
- 次のコミットに入れる予定のスナップショットを置く場所。

3. リポジトリ（HEAD）
- これまでのコミット履歴そのもの。HEADは現在のコミット位置。

多くのコマンドは、この3箇所のどこを更新するかが違うだけです。

## 2. よく使うコマンドがそう動く理由

### git add
ワーキングツリーの変更をインデックスへコピーするコマンドです。

- だから「編集しただけ」ではコミット対象にならない
- addした時点の内容が、次のコミット候補になる

### git commit
インデックスの内容を新しいコミットとして確定します。

- だからcommit前にaddが必要
- commitはワーキングツリーを直接は読まず、インデックスを読む

### git diff
比較対象によって見える差分が変わります。

- git diff: ワーキングツリー vs インデックス
- git diff --staged: インデックス vs HEAD

そのため「diffが空なのに変更したつもり」というときは、すでにadd済みで比較先が違うことがあります。

### git restore --staged <file>
インデックスだけを戻すコマンドです。

- ワーキングツリーは残る
- だから「コミット対象から外すだけ」ができる

### git restore <file>
ワーキングツリーの内容を、インデックス（または指定コミット）に合わせて戻します。

- だから未コミット変更が消えることがある
- 取り消し系で注意が必要な理由

### git reset --soft HEAD~1
ブランチ位置（HEAD）だけを1つ前へ戻し、インデックスとワーキングツリーは残します。

- だから「直前コミットだけなかったことにして、変更は残す」が可能
- --mixedや--hardと違い、破壊性が低い

## 3. ブランチとPR運用が安全な理由

ブランチは「コミットを指すポインタ」です。

- mainに直接コミットすると、本番系の履歴が直に動く
- 作業ブランチなら、mainを汚さずに差分確認できる
- PRは「どのコミットをmainに取り込むか」をレビュー可能にする仕組み

つまり、1タスク1ブランチ運用は、技術的には「ポインタの分離」で安全性を上げています。

## 4. コンフリクトが起きる理由

Gitは通常、自動マージで両方の変更を統合します。

同じ行付近を双方が編集していて、自動で正解を決められないと競合になります。

- `<<<<<<<` から `>>>>>>>` までは「どちらの変更を採用するか」を人間が決めるための印
- 解消後にaddするのは、「この解決結果を採用する」とGitへ伝えるため

## 5. pullで何が起きるか

`git pull` は実体として次の2段階です。

1. fetch: リモートの最新コミットを取得
2. merge（またはrebase）: 現在ブランチへ統合

そのため、pullでコンフリクトが起きるのはmerge/rebase段階です。

### なぜfetchを先に使うとよいか

- `git fetch` は履歴を取り込まず、リモート情報の更新だけを行う。
- 先にfetchしておけば、`origin/main` との差分を確認してから統合判断できる。
- いきなりpullするより、取り込み前のリスク確認ができるので事故を減らせる。

## 6. 迷いにくい判断基準

- 変更を次のコミットに入れたい: `git add`
- コミット対象から外したい: `git restore --staged`
- 作業自体を破棄したい: `git restore`
- 直前コミットだけ取り消したい（変更は残す）: `git reset --soft HEAD~1`

「今どこを変えたいか（ワーキングツリー / インデックス / HEAD）」で選ぶと、誤操作が減ります。

## 7. なぜこの流れを守る必要があるのか

この手順を守る必要があるのは、次の4つの事故を減らすためです。

- 意図しない差分をコミットしてしまう事故
- mainブランチを不安定にしてしまう事故
- コンフリクトを後回しにして解消コストが増える事故
- 変更理由が追跡できず、障害調査が長引く事故

Gitの操作は「面倒な儀式」ではなく、履歴品質と開発速度を両立するための安全装置です。
短期的には手順が増えて見えても、長期的にはレビュー効率と保守性が上がるため、結果的にチーム全体の開発を速くします。
