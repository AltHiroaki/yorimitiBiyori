# 実装計画

Flutter 版 `よりみち日和` の MVP を完成させるための実装計画です。仕様は [仕様書](../spec/仕様書.md)（詳細）と [仕様要約](../spec/仕様要約.md)（クイックリファレンス）を正とします。

直近の作業順は [これからやること](./これからやること.md)、Issue 作成用の分割は [工程計画](./工程計画.md) を参照してください。

---

## 進め方の方針

- **通知より先に、アプリ内で提案が完結する状態を作る**。通知は OS 依存が大きく検証コストが高いため、最後に「入口」として接続する
- **ロジックは UI から分離して先に作り、単体テストで固める**。画面はあとから差し替えられるが、ロジックの作り直しは高くつく
- **1 マイルストーン = 動くデモ**。各マイルストーンの終わりに、エミュレータで触れる状態を維持する
- Issue を立ててから着手し、ブランチは `issue-<Issue番号>-<短い内容>` 形式（例：`issue-12-suggestion-logic`）で切る。PR は必ず他メンバーがレビューする（[GitHub 開発フロー](../git/GitHub開発フロー.md)）

## M1: 提案が動く

### 1-1. モデル定義

新規ファイル：

- `lib/src/models/suggestion.dart` — `Suggestion`。`fromJson` は欠損フィールドで例外ではなく安全に失敗する（その 1 件をスキップ）
- `lib/src/models/user_settings.dart` — `UserSettings`。`selected_categories` / `detail_settings`（カテゴリ id → グループ id → 選択値の配列）/ `notification_enabled` / `notification_time` / `first_launch_completed` / `recent_suggestion_ids`。デフォルト値（カテゴリは [music, read, movie]、detail_settings は空＝指定なし）を持つ
- `lib/src/models/suggestion_record.dart` — `SuggestionRecord`。`estimated_minutes`（集計用）、`status`（done/skipped）と `feedback`（good/normal/bad/null）は enum にする
- `lib/src/models/interest_category.dart` — MVP 4 カテゴリ（music/cook/read/movie）の定数（id・表示名・絵文字）と、**カテゴリ別の詳細設定グループ定義**（MVP は「ジャンル」1 グループ、映画は「気分」）。散歩(walk)は `developmentCategories` として定義を残す。仕様書 3.4 の表が正

**完了条件**：モデルの fromJson/toJson 往復テストが通る。壊れた JSON を渡してもクラッシュしない。

### 1-2. データ読み込みと提案ロジック

新規ファイル：

- `lib/src/repositories/suggestion_repository.dart` — `rootBundle` から suggestions.json を読み、`List<Suggestion>` を返す。パース失敗は呼び出し側に伝わる形にする
- `lib/src/features/recommendation/suggestion_picker.dart` — **純粋関数**で実装：
  - `filterSuggestions(suggestions, settings)` — カテゴリ一致＋カテゴリ別詳細設定（タグ）のフィルタ（仕様書 6.1）。選択済みグループの値が `tags` に含まれること（グループ内 OR・グループ間 AND・カテゴリ間 OR）。未選択グループでは絞り込まない。予算項目選択時は `budget_yen` 上限で判定
  - `pickWeightedRandom(candidates, random)` — `Random` を引数で受け取りテスト可能にする
  - `excludeRecent(candidates, recentIds)` — 直近 3 件除外。候補が尽きたら直前 1 件のみ除外に緩和（仕様書 6.3）

**完了条件**：仕様書 10.1 の単体テスト（カテゴリ・詳細設定タグ・予算・直近除外・重み・履歴集計）がすべて通る。

### 1-3. 設定の保存

新規ファイル：

- `lib/src/repositories/settings_repository.dart` — shared_preferences への UserSettings 保存・読込。キーは `yorimiti_biyori_settings`。読込失敗時はデフォルト値に安全フォールバック

依存追加：`shared_preferences`（このタイミングで pubspec に追加）

### 1-4. 提案設定画面

## リスクと対策

| リスク | 対策 |
|---|---|
| 通知が機種・OS バージョンで動かない | M4 を MVP の最後に置き、M1〜M3 だけでもデモが成立する構成にしてある。実機確認を早めに 1 回挟む |
| ランダム通知で不都合な時間に通知される | 発展版では完全ランダムではなく、ユーザーが指定した時間帯の中だけでランダムにする。MVP では固定時刻通知に留める |
| shared_preferences のデータ形が途中で変わる | モデルに `fromJson` の安全フォールバックを必ず実装。形を変えるときは古いデータを捨てる判断を明示的に行う |
| Flutter 環境が未整備のメンバーがいる | [環境構築手順](../setup/環境構築手順.md) の最短手順を先に全員分終わらせる（M0 の残タスク） |
| 提案が偏る・つまらない | weight と直近除外で当面対応。データの追加は山本担当でいつでも並行可能 |
| スコープが膨らむ | 「MVP で実装しない機能」（仕様書 2.2）に載っているものは Issue を立てて発展行きにする |

## 実装時の注意

- MVP ではログイン・外部 API・AI API を入れない
- 通知より先に、アプリ内で提案が動く状態を作る
- AI API キーを Flutter アプリに直接入れない
- UI プロトタイプ（React）はデザイン参照専用で、コードを流用しない
- 仕様変更があったら、仕様書・仕様要約・このファイルを更新する
