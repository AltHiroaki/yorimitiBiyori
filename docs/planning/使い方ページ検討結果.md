## 結論

設定画面に「使い方」項目を追加し、専用ページへ遷移させる。掲載するのはIssue #139の検討案に挙がった5項目とし、静的テキストのみで構成する。提案画面の「使い方」カードは残し、末尾に「もっと詳しく」リンクを追加して使い方ページへ誘導する（案A）。「アプリについて」とは別ページとする。

Issue #139は方針決定までを対象とし、実装、既存仕様書の更新、テスト追加はFeature Issue #164で行う。#164が完了するまでは、現在のアプリに使い方ページがあるものとして扱わない。

## 現状の確認

- 設定画面は 提案設定 / 興味カテゴリ / テーマ / 通知時間帯・トグル / 履歴削除 の構成で、使い方に関する項目はない
- 提案画面の下部に「使い方」カードがあるが、内容は次の1文のみで薄い
  > カテゴリは条件カードのチップをタップすると、その場で切り替わります。詳細設定は「変更」から調整できます。通知をタップすると、保存した条件のよりみちが表示されます。
- 以下はオンボーディングでも提案画面のカードでも説明されておらず、ユーザーが自力で気づきにくい
  - 「詳しく見る」を押すと料理のレシピが開く
  - 「別の提案」を押すと、表示中の提案がスキップとして履歴に記録される
  - スキップした履歴をタップすると、その提案をもう一度やり直せる
  - 「やってみる」を押すと実施中の状態になり、完了するまで保持される
  - 通知は設定した時間帯の中でランダムな時刻に1日1回届く

## 決定事項

| 論点 | 決定 |
|---|---|
| 使い方ページを追加するか | 追加する |
| 掲載する項目 | 下記5項目 |
| 粒度 | 各項目1〜2文の静的テキスト。画像・アニメーションは含めない |
| 提案画面のカード（案A/B） | 案A：カードは残し、「もっと詳しく」で使い方ページへ誘導する |
| 「アプリについて」との統合 | 統合しない。役割が異なる別ページとする |
| MVPに含めるか | 含めない。MVP完了後の発展機能とする |

### 掲載する5項目

1. **よりみち日和の使い方** — 提案が届く → やってみる → 完了 → 履歴に残る
2. **提案が合わないときは** — スキップして次へ／詳細設定で絞り込む
3. **スキップした提案をもう一度** — 履歴からタップすると復活できる
4. **料理のレシピを見る** — 「詳しく見る」で展開できる
5. **通知について** — 設定した時間帯の中で1日1回届く

## 判断の根拠

### 追加するか

オンボーディングは「1周の流れ」を伝える場であり、機能の詳細を足すと画面が長くなるうえ、そのUIに出会う前の説明は記憶に残らない。一方でIssue #139が挙げた5点は、対応するUIに実際に触れた後でないと必要性が実感しにくく、かつ現在はどこにも再確認できる場所がない。したがって、いつでも読み返せる専用ページを設ける。

### 提案画面のカードとの関係（案A採用）

案Bのようにカードを削除して設定へ一本化すると、提案タブは多少すっきりするが、使い方の説明に最も近いタイミング（提案を見ている最中）での導線が消える。カード自体は残して短い要約のままとし、詳しく知りたい場合だけ使い方ページに進めるようにすれば、提案タブの分量を増やさずに導線を確保できる。設定画面からの遷移と合わせて、入口を2つ持たせる。

### 静的テキストのみ

MVP完了を優先する方針（`docs/rules/AGENTS.md`）に沿い、画像やアニメーションによる説明強化は行わない。テキストのみでも5項目の説明は成立する。

### 「アプリについて」と分ける

「アプリについて」はバージョン情報など静的なメタ情報を扱う想定であり、操作説明とは更新頻度も目的も異なる。1ページにまとめると項目が混在してわかりやすさを損なうため分ける。

### MVPに含めない

`docs/rules/AGENTS.md`のMVP Featuresには使い方ページが含まれていない。現状のカードとオンボーディングで最低限の導線はあるため、MVP完了を優先し、使い方ページはMVP完了後の発展機能として扱う。
