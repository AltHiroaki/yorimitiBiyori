# GitHub Projects 運用方針

## 目的

GitHub Projects はタスク管理ではなく、プロジェクト全体の進捗を把握するために利用する。

- Issue = 作業内容
- Pull Request = 実装結果
- Project = 現在の進捗状況

## 基本方針

Project には細かいタスクを載せすぎない。

推奨粒度：

- 提案機能
- 履歴機能
- 設定機能
- テスト
- 発表準備

## ステータス（カンバンの列）

進捗は GitHub Projects の Status 列で管理する。本プロジェクトでは次の 5 つを使う（**Project #4 の設定を正とする**）。

| 列 | 意味 |
|---|---|
| バックログ | まだ着手していない。これからやること |
| 着手予定 | 次に着手する予定（任意。使わなくてもよい） |
| 作業中 | いま作業している |
| レビュー中 | Pull Request を出してレビュー待ち |
| 完了 | マージ済み・対応済み |

「着手予定」は無理に使わなくてよい。最低限 **バックログ → 作業中 → レビュー中 → 完了** の流れで動かせば十分。

## 管理項目

Project #4 には多くのフィールドがあるが、最低限は以下だけ管理すれば十分。

|フィールド|説明|
|---|---|
|Status|現在の状態（上のカンバン列）|
|Assignee|担当者|
|Milestone|どのマイルストーンに属するか（例：`M1 提案が動く`）|
|Priority|優先度（`P0`／`P1`／`P2`。任意。Issue 側のラベル `priority:high/medium/low` と役割が重複するので、どちらか一方を主に使う）|

振り返り用に着手日・完了日を残したい場合は、`Start date` / `Target date` フィールドを使う。

## 開始日・終了日を記録する理由

開始日と終了日を残しておくことで、後から振り返りができる。

例：

- どの機能に時間がかかったか
- 見積もりが正しかったか
- どこで詰まったか

## 学生開発向けの考え方

本プロジェクトは小規模開発であるため、Story Point や Velocity などの高度な指標は管理しない。

まずは以下を徹底する。

1. Issue を作る
2. ブランチを切る
3. Pull Request を出す
4. レビューする
5. Project を更新する
