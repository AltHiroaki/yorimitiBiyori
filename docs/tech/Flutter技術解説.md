# Flutter 技術解説

このドキュメントは、`よりみち日和` を Web アプリではなく Flutter による Android アプリとして作る理由と、使う技術の役割を説明するものです。iOS は MVP 完成後の発展版で導入します。

---

## 結論

`よりみち日和` は、空き時間に通知を送り、通知上のボタンから 15 分 / 30 分 / 60 分を選ぶことで、ユーザーの興味に合う提案をすぐ表示するアプリとして設計します。

この体験は、ユーザーが自分から Web サイトを開くよりも、スマホ通知を起点にした方が自然です。

そのため、MVP では Flutter を使って Android 向けのネイティブアプリとして開発します。

---

## なぜ Web アプリではなく Flutter なのか

今回のコア体験は以下です。

```text
通知が届く
↓
15分 / 30分 / 60分 を選ぶ
↓
アプリが開く
↓
すぐ提案が表示される
```

Web アプリでも画面表示や提案ロジックは作れます。

しかし、通知アクションやローカル通知を主機能にする場合、スマホ OS の通知機能と自然に連携できるネイティブアプリの方が向いています。

Flutter なら、MVP では Android 版を先に作りつつ、発展版で iOS に展開するときも画面やロジックを共有できます。

---

## Flutter を選ぶ理由

### 1. 発展版で iOS に展開しやすい

完全ネイティブ開発では、iOS は Swift、Android は Kotlin で別々に実装する必要があります。

Flutter では、Dart で書いたコードをもとに Android と iOS の両方へ展開できます。MVP では Android のみを対象にし、iOS は発展版で追加します。

これにより、以下を共通化しやすくなります。

- 画面
- 提案ロジック
- 提案データの読み込み
- 履歴保存の処理
- 設定画面
- テスト

### 2. 通知機能と相性がよい

MVP では、ローカル通知を使ってユーザーに空き時間を選んでもらいます。

```text
[15分] [30分] [60分]
```

通知ボタンを押すと、選んだ時間をもとに提案画面を表示します。

Flutter では通知用パッケージを使うことで、ローカル通知や通知アクションを扱えます。

ただし、通知は OS 機能に依存するため、MVP では Android Emulator と Android 実機で確認します。iOS の通知確認は発展版で行います。

### 3. UI を整理しやすい

Flutter は Widget を組み合わせて画面を作ります。

画面要素もレイアウトも Widget として扱うため、UI を部品単位に分けやすいです。

例：

```dart
Text('よりみち日和')
FilledButton(
  onPressed: () {},
  child: Text('やってみる'),
)
```

### 4. テストしやすい

Flutter では、以下のようにテストを分けられます。

| 種類 | 何を確認するか |
|---|---|
| Unit test | 提案ロジックやデータ変換など、画面に依存しない処理 |
| Widget test | ボタン、カード、空状態などの UI 表示 |
| Integration test | アプリ全体の流れ |

`よりみち日和` では、まず以下をテスト対象にします。

- 選択時間以内の提案だけ出るか
- 興味カテゴリに合う提案だけ出るか
- 候補がない場合に空状態を返せるか
- 履歴の実施数・スキップ数を正しく数えられるか

通知そのものは OS 依存が大きいため、自動テストだけで完結させず、実機確認も必要です。

## 主な技術構成

| 技術 | 役割 |
|---|---|
| Flutter | Android アプリの UI とロジックを作り、発展版で iOS に展開しやすくする |
| Dart | Flutter アプリを書く言語 |
| Material 3 | スマホ向け UI コンポーネントの基盤 |
| flutter_local_notifications | ローカル通知と通知アクションを扱う候補 |
| shared_preferences | 端末内に簡単な設定・履歴を保存する候補 |
| flutter_test | ロジック・Widget テストを行う |

MVP では、外部サービス連携やクラウド保存は使いません。

## MVP で使うデータ

提案候補は以下で管理します。

```text
assets/data/suggestions.json
```

MVP では、ユーザーが登録した興味カテゴリと、通知で選んだ時間をもとに候補を絞ります。

```text
ユーザーの興味: 音楽, YouTube, 読書
選択時間: 30分
↓
interest_tags に合う
かつ duration_minutes <= 30
↓
ランダムに1件表示
```

## 実装方針

### 画面とロジックを分ける

画面ファイルに複雑な提案ロジックを書きすぎないようにします。

悪い例：

```text
suggestion_page.dart の中で JSON 読み込み、絞り込み、ランダム選択、履歴保存を全部行う
```

良い例：

```text
pages/ は表示とユーザー操作を担当
features/recommendation/ は提案ロジックを担当
features/records/ は履歴保存を担当
```

### MVP では状態管理を複雑にしない

最初から状態管理ライブラリを全面的に導入すると、学習量と実装量が増えます。

MVP では、まず Flutter 標準の `StatefulWidget` や `ValueNotifier` で足りる範囲にします。

画面間で共有する状態が増えてきたら、Riverpod などの導入を検討します。

### 通知は段階的に入れる

通知機能は OS 依存があるため、いきなり完成形を作ろうとしない方が安全です。

順序は以下にします。

```text
1. アプリ内でカテゴリ＋詳細設定を選んで提案する
2. ローカル通知を1件出す（文言は時間を名指ししない。例「暇な時間って存在しますか？」）
3. 通知をタップしてアプリを開く
4. 保存済みのカテゴリ＋詳細設定で提案画面を表示する
```

## Android / iOS の確認

### Android

Android Studio の Android Emulator で確認できます。

Windows / macOS / Linux で利用できます。

### iOS

iOS は MVP では対象にしません。発展版で導入する段階では、macOS と Xcode が必要です。

Windows だけでは iOS Simulator は使えません。

### 実機確認

通知は端末設定、ロック画面、バッテリー制御、OS バージョンの影響を受けます。

そのため、MVP では Android 実機確認を行い、発展版で iOS を導入するときに iPhone 実機確認を行います。

## 発展機能の扱い

以下は MVP 完成後に検討します。

- iOS 版の生成、ビルド、実機確認
- iOS 通知許可・ローカル通知対応
- AI による提案候補生成
- YouTube 連携
- 音楽サービス連携
- Google Calendar 連携
- 位置情報
- クラウド保存

MVP では、AI や外部サービスがなくても動くように、静的な提案データとランダム提案で成立させます。

---

## まとめ

Flutter を選ぶ理由は、単に新しい技術を使いたいからではありません。

`よりみち日和` の中心体験が、スマホ通知をきっかけにした提案だからです。

```text
通知 → 時間選択 → 即提案
```

この流れを安定して作るために、Web アプリより Flutter によるネイティブアプリ化の方が適しています。
