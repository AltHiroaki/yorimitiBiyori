# 製品概要と課題：よりみち日和

作成日：2026年7月5日 ／ 対象：main ブランチ（PR #35 マージ時点）

このドキュメントは、よりみち日和の **①現在の実装方針、②MVP 以外の発展機能の提案、③セキュリティに関する問題点、④UI/UX の既知の課題** を1か所にまとめたものです。チームメンバー向けを基調とし、冒頭のサマリーは発表資料にも流用できます。

---

## 概要サマリー（発表向け）

- **よりみち日和**は、好きなカテゴリ（音楽・料理・読書・映画）を選び、ジャンルなどの簡単な詳細設定で好みを絞り込むと、「いつもとは違うもの」を説明つき（料理はレシピつき）でランダムに1件提案する Android アプリです（Flutter 製）。
- 実装方針は「**小さく確実に**」：ログイン・サーバー・外部 API を使わず端末内で完結させ、中心機能（カテゴリ選択 → 詳細設定 → 提案 → 履歴保存）を先に安定させてから通知などを足します。
- 進捗は **M0〜M3（骨格・提案・履歴・オンボーディング）が完了**し、残りは M4（通知）と M5（仕上げ）です。テストは 84 件が自動で通る状態を維持しています。
- セキュリティ面は、**完全オフライン・個人情報の不収集・最小権限**という設計自体が最大の防御になっており、現時点で悪用可能な問題はありません。ただし**一般公開前に必ず直す設定が2点**（リリース署名・バックアップ設定）あります。

## 1. 現在の実装方針

### 1.1 プロダクト設計：二段階方式（企画書 ver6）

| 項目 | 方針 |
|---|---|
| 中心操作 | **カテゴリ選択 → カテゴリ別の詳細設定**の二段階。必須の共通条件は持たず、その後に任意の「時間の上限」（指定なし/15/30/60分）だけを安全上限として適用できる |
| MVP コアカテゴリ | 音楽・料理・読書・映画の 4 種（散歩は発展カテゴリとして定義・データを先行整備済み） |
| MVP の詳細設定 | 各カテゴリ「ジャンル」系 1 グループのみ。複数グループ化は発展機能 |
| 提案カード | タイトル・説明・タグを表示する。料理は**レシピ（recipe）**を「詳しく見る」から展開でき、「知らないものでも試せる」状態にする |
| 通知 | 時間（分数）を名指ししない柔らかい誘い（例「暇な時間って存在しますか？」）。通知は開くきっかけに徹し、提案は保存済み条件から生成 |

### 1.2 技術方針：ローカル完結・最小依存

| 項目 | 内容 |
|---|---|
| スタック | Flutter / Dart / Material 3（グリーン基調 `#3F6F44`） |
| データ | 提案候補は `assets/data/suggestions/<category>.json`（カテゴリ別・アプリ同梱）、設定・履歴は shared_preferences |
| 通信 | **一切なし**（ネットワークコード 0 件。直接依存は shared_preferences 等 3 パッケージのみ） |
| ログイン | なし。個人情報（氏名・メール・位置情報・カレンダー）を扱わない |
| 状態管理 | StatefulWidget ＋ コンストラクタ注入（repository をテストで差し替え可能にする統一パターン） |

### 1.3 開発の進め方

- **ロジックを UI から分離し、純粋関数＋単体テストで固める**（提案フィルタ・weight 抽選・履歴集計は `lib/src/features/` に分離済み）
- **通知（OS 依存が大きい）は最後**。アプリ内で体験が完結してから M4 で接続する
- Issue 番号ベースのブランチ（`issue-<番号>-<内容>`）→ PR → レビューのフロー。コード変更後は `flutter analyze` / `flutter test` を必須とする

### 1.4 マイルストーン進捗（2026年7月5日時点）

| MS | 内容 | 状態 |
|---|---|---|
| M0 | 3タブ骨格・提案データ・ドキュメント | ✅ 完了 |
| M1 | モデル・提案ロジック・提案設定画面（二段階） | ✅ 完了 |
| M2 | 完了モーダル・記録・履歴画面・履歴削除 | ✅ 完了（PR #31〜#33, #35） |
| M3 | オンボーディング | ✅ 完了（PR #34） |
| M4 | ローカル通知（flutter_local_notifications は未導入） | ⬜ 未着手 |

テスト：84 件全パス／`flutter analyze` クリーン（PR #35 時点）。

## 2. 発展機能：新規提案

既存の発展計画（仕様書 13 章）は以下の通り確定済みです。

| 段階 | 既存計画 |
|---|---|
| Phase 1 | 候補増加（各詳細設定の選択肢につき50件以上、MVP全選択肢で対応済み）・カテゴリ追加（散歩など）・**詳細設定の複数グループ化**・通知時間帯ランダム化・Claude API による料理レシピ（recipe）動的生成・実施率（履歴の期間・ステータスフィルターは実装済み） |
| Phase 2 | iOS 対応（platform 生成・通知確認・TestFlight） |
| Phase 3 | Firebase Authentication・Cloud Firestore・Cloud Functions |
| 将来構想 | Google Calendar・位置情報・YouTube/音楽サービス連携 |

その上で、**このリポジトリの実装を踏まえた新規提案**を優先度付きで挙げます。判断基準は「ライト層に小さなきっかけを出す」というコンセプトとの整合と、現在の設計からの実装コストです。

### 優先度：高（コンセプト直結・低コスト）

| 提案 | 内容 | なぜこの製品に合うか / コスト感 |
|---|---|---|
| **フィードバック学習** | 完了モーダルで収集済みの good / normal / bad を使い、タグ単位で weight を自動調整する（bad が続くタグは出にくく、good のタグは少し出やすく） | **フィードバックは既に保存しているのに現状どこにも使われていない**。既存の weight 付き抽選にそのまま乗るため追加実装が小さく、「使うほど自分に合う」体験はライト層の継続動機になる |
| **「あとでやる」ブックマーク** | 提案カードに「あとで」を追加し、ピン留めした提案を履歴タブ（または提案タブ）から呼び出せるようにする | 「今はできないが面白そう」の受け皿がなく、現状はスキップ（＝ネガティブ記録）しか選べない。records の status に `saved` を足すだけで成立する |
| **週間振り返りサマリー** | 週1回「今週は◯回よりみちしました」を通知またはアプリ内カードで表示 | 履歴集計ロジック（record_summary）が完成済みで、期間フィルタを足すだけ。小さな達成感がリテンションに効く |

### 優先度：中（価値は高いが設計追加が必要）

| 提案 | 内容 | なぜ / コスト感 |
|---|---|---|
| **時間帯コンテキスト** | 朝は軽め・夜はリラックス系など、時刻に応じて weight を補正 | 「時間条件の廃止」で失った文脈性を、ユーザー操作を増やさずに取り戻せる。タグ×時間帯の補正表が必要 |
| **ホーム画面ウィジェット** | Android ウィジェットに「今日のよりみち」を常時表示 | 通知より押しつけがましくない入口。home_widget パッケージ導入と表示専用レイアウトが必要 |
| **設定・履歴のエクスポート / インポート** | JSON ファイルへの手動書き出し・読み込み | Phase 3（Firebase）を待たずに機種変更へ対応できる。既存の toJson/fromJson がそのまま使える |
| **提案データのリモート更新** | 起動時にカテゴリ別提案JSONの新版を取得（失敗時は同梱版へフォールバック） | アプリ更新なしで候補を増やせる。ただし**初のネットワーク通信**になるためセキュリティ節の将来リスクとセットで検討 |

### 優先度：低（余裕があれば）

| 提案 | 内容 | なぜ / コスト感 |
|---|---|---|
| ゆるいゲーミフィケーション | 連続記録（ストリーク）や「5カテゴリ制覇」バッジ | 楽しいが、過度な義務感はコンセプト（ゆるさ）と相反するため控えめに |
| よりみち共有 | OS シェアシートで提案テキストを共有 | share_plus 1つで実装可能。バイラル効果は限定的 |
| ダークモード | Material 3 の ColorScheme 切替 | seed color 方式なのでコストは小さいが、体験価値への寄与も小さい |

**推奨**：M5（MVP 完成）後の最初の一手は**フィードバック学習**。収集済みデータを活かせる唯一の提案であり、企画書の課題「体験の固定化」への回答を1段深くできる。

## 3. セキュリティ：現状評価と問題点

### 3.1 できていること（設計による防御）

- **完全オフライン**：ネットワークコードが存在せず（http/dio/socket の import 0 件）、通信起点の攻撃面がない
- **最小権限**：AndroidManifest に危険権限の宣言なし（INTERNET は debug ビルド専用、POST_NOTIFICATIONS も未宣言＝M4 で追加予定）
- **PII 不収集**：氏名・メール・位置情報・カレンダーを扱わない。保存するのは興味カテゴリ・詳細設定・実施/スキップ履歴のみ
- **防御的パース**：カテゴリ別提案JSON・保存データとも、型ガードと FormatException ハンドリングで壊れたデータを安全にスキップ（`suggestion_repository.dart` / `records_repository.dart`）
- **ログにユーザーデータを出さない**：`lib/` に print / debugPrint が 0 件
- **秘密情報の管理**：keystore / key.properties は `.gitignore` 済みで、リポジトリに秘密のコミットなし
- **削除手段の提供**：履歴削除（インライン確認付き・取り消し不可の明示）を実装済み（仕様書 §9 のプライバシー方針と一致）

### 3.2 問題点（優先度順）

| # | 優先度 | 問題 | 場所 | 対応 |
|---|---|---|---|---|
| 1 | **Critical（一般公開前に必須）** | **リリースビルドがデバッグ鍵で署名**されている。デバッグ鍵は誰でも生成でき、なりすましアップデートのリスクがあるほか、Play ストアに提出できない | [build.gradle.kts:32](../../android/app/build.gradle.kts)（`signingConfig = signingConfigs.getByName("debug")`、TODO コメントあり） | リリース用 keystore を生成し signingConfig を差し替える。keystore は `.gitignore` 済みの `key.properties` 経由で読む |
| 2 | **High（1行で直る・M4 前推奨）** | `android:allowBackup` が未設定（デフォルト true）。`adb backup` や機種移行で shared_preferences の中身（設定・履歴）が抽出され得る | [AndroidManifest.xml:2](../../android/app/src/main/AndroidManifest.xml)（`<application>` に属性なし） | `android:allowBackup="false"` を追加（クラウド同期を正式導入する Phase 3 で再検討） |
| 3 | **Medium（公開前に必須・実害は小）** | `applicationId` が `com.example.yorimichi_biyori` のまま。`com.example` は Play ストアに公開できないプレースホルダ | [build.gradle.kts:19](../../android/app/build.gradle.kts)（TODO コメントあり） | 公開前に独自のパッケージ名へ変更（変更するとアプリ ID が変わるため早めが安全） |
| 4 | **Medium（MVP では許容）** | 設定・履歴が shared_preferences に**平文 JSON** で保存される。root 化端末や上記 #2 経由で読み取り可能 | `settings_repository.dart` / `records_repository.dart` | 保存内容に機微情報がないため MVP では許容。クラウド同期・アカウント導入（Phase 3）の際に flutter_secure_storage 等を再検討 |
| 5 | **Low（M4 実装時の注意）** | 通知ペイロードに履歴や設定の詳細を含めると、ロック画面に表示され得る | M4 実装時 | 通知文言は固定の誘い文句のみとし、ユーザーデータを載せない（現仕様の文言方針なら自然に満たせる） |

### 3.3 発展機能導入時の将来リスク

発展機能は「攻撃面の追加」と表裏一体です。導入時に以下を必ず守ります（仕様書 §9 の方針を再掲・具体化）。

| 導入するもの | リスク | 守ること |
|---|---|---|
| Claude API（Phase 1） | API キー漏えい・コスト踏み逃げ | **キーをアプリに埋め込まない**。Cloud Functions 経由で呼び、クライアントにはキーを渡さない。生成結果は検証してから表示（危険な行動・高額前提の提案を弾く） |
| 提案データのリモート更新（本ドキュメント提案） | 初のネットワーク通信。改ざんされた JSON の配信 | HTTPS 固定・スキーマ検証・失敗時は同梱版へフォールバック。INTERNET 権限追加の影響を README に明記 |
| Firebase Auth / Firestore（Phase 3） | 他ユーザーのデータ読み書き | Security Rules で `request.auth.uid` によるユーザー単位の読み書き制限を必ず設定してからリリース |
| クラウド同期（Phase 3） | 履歴（行動パターン）がサーバーに乗る | 同期はオプトイン・削除機能（ローカル＋クラウド両方）をセットで提供。この段階で保存の暗号化を再評価 |

## 4. UI/UX：既知の課題

### 4.1 条件カードのカテゴリチップは、カテゴリ数が増えるとスケールしない

| 項目 | 内容 |
|---|---|
| 場所 | `lib/src/pages/suggestion_page.dart` の `_ConditionCard`（issue #149 で `FilterChip` 化） |
| 前提 | 提案タブの条件カードに**全カテゴリを常に並べ**、タップで即オン/オフ・即保存・即再抽選する設計 |
| 成り立っている理由 | カテゴリが MVP 4 種＋散歩の**計 5 件しかない**ため、`Wrap` で 2 行に収まり、提案カードを画面外へ押し出さない |
| 破綻する条件 | 発展機能でカテゴリ（運動・芸術など）を追加し、**おおむね 8 件を超えたあたり**からチップが 3 行以上に伸びる。文字サイズ拡大時はさらに早く破綻する |
| 起きること | 条件カードが縦に肥大化し、提案タブを開いた瞬間に「今日のよりみち」カードが見えなくなる。主役である提案より条件のほうが目立つ状態になる |

**カテゴリを追加するときに、あわせて検討すること**（いずれも未着手）：

- **横スクロール化**：チップを 1 行の横スクロールにする。省スペースだが、隠れた選択肢に気づきにくい
- **上位数件＋「他 N 件」**：選択中のカテゴリだけをカードに出し、残りは展開して表示する
- **ボトムシート編集へ移行**：カードはタップ領域だけにし、条件の編集はボトムシートで行う（提案設定画面と UI が二重管理になる点に注意）

判断の目安：**カテゴリが 8 件を超えたら、チップ直置きは一度やめて上の 3 案を比較する。**
