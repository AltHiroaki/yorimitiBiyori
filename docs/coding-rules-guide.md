# コーディング規則の考え方：Flutter版

このドキュメントは、よりみち日和のFlutter版を実装するときに、なぜ現在のコーディング規則を守るのかを説明するためのものです。

AI agentに直接読ませる規則は、以下にまとめています。

- [General Coding Skill](./SKILL.md)
- [AI Agent Rules for yorimitiBiyori](./AGENTS.md)

## 1. MVPを優先する理由

よりみち日和では、まず次の流れを安定させることを優先します。

```text
興味登録 → 時間選択 → 提案表示 → 実施またはスキップ記録 → 履歴表示
```

Google Calendar、位置情報、AI API、YouTube連携などは魅力的ですが、最初から入れると実装範囲が広がりすぎます。

MVPでは、端末内の設定と静的JSONデータだけで中心体験を作ります。

## 2. 技術スタックをFlutterに固定する理由

現在のよりみち日和は、MVP では Android 向けの Flutter アプリとして開発します。iOS は MVP 完成後の発展版で導入します。

通知を使ってユーザーに提案を届ける体験が中心になるため、Webアプリよりもスマートフォンアプリのほうが合っています。

新しい実装では、React、Vite、Tailwind、React Routerを使いません。旧Web版のファイルは `archive/old-web-version/` に移動しています。

## 3. UIとロジックを分ける理由

FlutterのWidgetに、提案データの読み込み、絞り込み、ランダム選択、履歴保存まで詰め込むと、画面が大きくなりすぎます。

ページWidgetは画面の組み立てとユーザー操作の受け取りを担当し、提案ロジックや保存処理は別のクラスや関数に分けます。

例：

```text
lib/src/pages/suggestion_page.dart
lib/src/features/recommendation/
lib/src/repositories/
lib/src/models/
```

こうしておくと、画面の見た目を直す作業と、提案条件を変える作業が混ざりにくくなります。

## 4. モデルを明示する理由

提案、ユーザー設定、履歴はアプリの中心データです。

Mapやdynamicをそのまま画面で扱うと、フィールド名の間違いやnullの扱いでバグが起きやすくなります。

そのため、次のようなモデルを用意します。

- `Suggestion`
- `UserSettings`
- `SuggestionRecord`

JSONの構造を変える場合は、モデル側も合わせて更新します。

## 5. 提案ロジックを単純に保つ理由

MVPでは、複雑な推薦アルゴリズムは使いません。

基本の条件は次の2つです。

- 提案の所要時間が、ユーザーの選択時間以内である
- 提案の興味タグが、ユーザーの興味カテゴリと重なる

候補が見つかったら、その中からランダムに1件を選びます。

重み付け、AI生成、外部サービス連携は、中心機能が動いてから検討します。

## 6. 保存処理を専用の場所に分ける理由

MVPではログインを使わないため、設定や履歴は端末内に保存します。

保存処理を画面に直接書くと、保存キーやデータ形式の変更時に修正漏れが起きやすくなります。

そのため、端末内保存はrepositoryにまとめます。

```text
lib/src/repositories/
```

保存データは壊れている可能性があるものとして扱い、読み込みに失敗してもアプリが落ちないようにします。

## 7. 依存パッケージを増やしすぎない理由

依存パッケージを増やすと、実装は短くなることがありますが、管理するものも増えます。

MVPでは、Flutter標準で作れる部分は標準機能を使います。

通知や端末内保存のように必要性がはっきりしているものだけ、導入理由を確認してから追加します。

## 8. 変更後に確認すること

コードを変更した後は、可能な範囲で以下を実行します。

```bash
flutter analyze
flutter test
```

通知機能を触った場合は、MVP では Android Emulator と Android 実機での確認が必要です。iOS Simulator と iPhone 実機での確認は、発展版で iOS を導入するときに行います。

確認できなかった場合は、何が未確認かを明記します。
