# 仕様要約：よりみち日和

このファイルは、`よりみち日和` の現在の仕様を実装者向けに要約したものです。詳細は [仕様書.md](./仕様書.md) を参照してください。

仕様の正本は **企画書 ver6（2026年提出版 PDF）** と **`よりみち日和 UIプロトタイプ/`（Figma 書き出し）** です。
両者が食い違う場合、提案条件まわり（二段階方式）はデザインの正本である企画書を優先し、その他の画面構成・UI 文言・操作フローはプロトタイプを参照します。プロトタイプの提案設定画面は旧モデルのため**要更新**です。

> ver6 の主な変更：MVP のコアカテゴリを **音楽・料理・読書・映画の 4 種類**に整理（散歩は発展カテゴリ）、MVP の詳細設定を各カテゴリ **「ジャンル」1 種類のみ**に絞る。

---

## アプリ概要

よりみち日和は、ユーザーが選んだ興味カテゴリと、そのカテゴリ固有の詳細設定をもとに、空き時間でできる小さな「よりみち」を 1 件提案する Android 向け Flutter アプリです。MVP では Android のみを対象にし、iOS 対応は MVP 完成後の発展版で導入します。

- 企画コンセプトコピー：「好きなことで、いつもと違う角度から。」
- アプリ内タグライン：「空いた時間に、小さなよりみちを。」
- 差別化の核心：「好きな領域の中で、知らなかった自分の好みと出会える」

中心機能は「**カテゴリ選択 → 詳細設定 → 提案 → 履歴保存**」です。

## 提案条件（二段階方式）

提案は **2 段階** で絞り込みます。**難易度・移動距離・共通の使える時間は廃止**しました。

1. **第 1 段階：カテゴリ選択**（複数選択可。MVP は音楽・料理・読書・映画の 4 カテゴリ）
2. **第 2 段階：選択カテゴリごとの詳細設定**（カテゴリ固有。**MVP は各カテゴリ「ジャンル」1 グループを基本**とし、料理のみ「調理法」を加えた2グループ。各グループは未選択＝指定なし＝絞り込まない）

絞り込みルール：カテゴリ一致 ＋ 選択済み詳細設定グループの値が提案の `tags` に含まれること。グループ内 OR、グループ間 AND、カテゴリ間 OR。

初期表示：カテゴリ初期値は［音楽・読書・映画］。詳細設定はすべて未選択（指定なし）。

### カテゴリ（マスター定義）

MVP コアは 4 カテゴリ。散歩は発展カテゴリとして定義・データを残します（`InterestCategories.developmentCategories`）。

| id | 表示名 | 絵文字 | 区分 |
|---|---|---|---|
| music | 音楽 | 🎵 | MVP |
| cook | 料理 | 🍳 | MVP |
| read | 読書 | 📖 | MVP |
| movie | 映画 | 🎬 | MVP |
| walk | 散歩 | 🚶 | 発展 |

### カテゴリ別の詳細設定（MVP・企画書 ver6 表3 準拠）

MVP は各カテゴリ「ジャンル」1 グループを基本とするが、料理のみ「調理法」グループを追加する。

| カテゴリ | グループ | 選択肢 |
|---|---|---|
| 音楽 | ジャンル | ポップス / ジャズ / クラシック / 洋楽 / ロック / ヒップホップ・R&B / アニソン・ゲーム音楽 / EDM・テクノ |
| 料理 | 味覚・ジャンル | 和食 / 洋食 / 中華 / イタリアン / アジア風 / 激辛 / さっぱり / ガッツリ |
| 読書 | ジャンル | エッセイ / 小説 / ノンフィクション / 詩集 / ミステリー・サスペンス / SF・ファンタジー / ビジネス・自己啓発 / 歴史・教養 |
| 映画 | ジャンル | アクション / コメディ / ドラマ / SF / サスペンス / ファンタジー / 恋愛 / アニメ / ミステリー |
| 散歩（発展） | 目的 | 気分転換 / 運動 / 発見 |

> 映画は 1 作品に複数ジャンルをタグ付けできる（`tags` は `List<String>`）。料理は「味覚・ジャンル」×「調理法」の2グループをAND条件で絞り込む。

発展で追加する詳細設定（企画書 ver6 表3 の「発展版で追加」）：音楽＝言語・気分、料理＝栄養素・ダイエット、読書＝読書時間・入手予算、映画＝上映時間・視聴先。

注：散歩の詳細設定は企画書に明記がないため本仕様で補完したものです。運動・芸術などは同じパターンで発展追加できます。

## 画面構成

ボトムナビゲーション 3 タブ構成です。**ホーム画面はありません**（提案タブがトップ画面）。

| 画面 | 役割 |
|---|---|
| 提案（タブ1） | 現在の提案条件カード（カテゴリ＋詳細設定）と「今日のよりみち」カードを表示し、案内カードから使い方ページへ遷移できる |
| 履歴（タブ2） | 実施・スキップの集計と履歴一覧を表示する |
| 設定（タブ3） | 提案設定・興味カテゴリ・通知・使い方・履歴削除を管理する |
| 提案設定（サブ画面） | カテゴリ選択 → カテゴリ別詳細設定を編集する（二段階） |
| 使い方（サブ画面） | 基本の流れ、スキップ、履歴からの復活、料理レシピ、通知を静的テキストで案内する |
| オンボーディング | ようこそ画面 → カテゴリ選択 → 通知許可（3画面とも全画面） |
| 提案完了モーダル | 「やってみる」後のフィードバック入力 |
| 履歴空状態 | 履歴 0 件のときの表示 |

タブは下タブのタップと横スワイプ（隣接のみ）で切り替えます。隣接はスライド、提案 ↔ 設定の飛び越しは履歴を見せないフェード、完了 → 履歴だけは長め（400ms）のスライド＋フェードで区別します（詳細は仕様書 4.1）。

### 提案画面

- ヘッダー：アプリ名「よりみち日和」＋タグライン「空いた時間に、小さなよりみちを。」
- **現在の提案条件カード**：全カテゴリの FilterChip（選択中のみ selected）。**タップでその場で切り替わり、保存して再抽選**する。1 件のときは解除不可（SnackBar で通知）。右上に「◯つ選択中」。下部に有効な詳細設定の要約（未選択時は「詳細設定：すべてのジャンルから」）＋「変更 >」→ 提案設定画面へ
- **今日のよりみちカード**：タイトル（大見出し）、説明文、料理のみレシピ（`recipe`）を展開する「詳しく見る」、タグチップ、補助色の「目安 約N分」、続けて「入手先：〜」（`where_to_try`）。所要時間はタグではなく参考情報として表示。ボタン 2 つ「やってみる」／「スキップして次の提案」

### 提案設定画面（二段階）

1. カテゴリ選択：FilterChip 複数選択（MVP 4 種、絵文字付き）＋「◯つ選択中」
2. 選択した各カテゴリの詳細設定：カテゴリごとにセクションを表示し、固有のグループを FilterChip（複数選択）で並べる。未選択は「指定なし」

下部固定：「この条件で保存」／「初期設定に戻す」。

### 履歴画面

- 期間セグメント：**今週 / 全期間**。初期値は今週。今週は端末ローカル時刻の月曜日 00:00 から現在まで
- サマリーカード（3 分割）：選択期間の **実施数 / スキップ数 / 合計時間（分）**（合計時間は期間内の done レコードの `estimated_minutes` 合計）。ステータスフィルタでは変えない
- ステータスフィルタ：**すべて / 実施 / スキップ**の単一選択。初期値はすべて
- 「今週の履歴」または「最近の履歴」リスト：ステータスアイコン、タイトル、日付、タグ・所要時間、実施/スキップバッジ
- 保存済み履歴 0 件は「まだ履歴はありません」＋「提案を見てみる」。絞り込み 0 件は「今週の履歴はありません」または「この条件の履歴はありません」＋条件変更ボタン
- 絞り込み状態は保存せず、通常のタブ切替では HistoryPage の State に保持する。完了直後は保存した履歴が見える条件へ補正してハイライトする

### 設定画面

- 基本設定：Google アカウント（未連携・発展版）／提案設定（カテゴリと詳細設定を調整）／興味カテゴリ／通知時間帯（開始・終了、デフォルト 17:00〜21:00。開始 > 終了はエラー）／通知トグル
- データ：履歴削除（赤字・インライン確認）／アプリについて

### オンボーディング

初回起動時のみ。3ステップを維持し、全画面の上部に「ステップ n / 3」とプログレスインジケーターを表示する。3ステップとも全画面ページで、モーダルは使わない。2ステップ目以降は戻るボタンと端末の戻る操作で前へ戻れ、カテゴリの選択は保持される。

1. ようこそ画面：「よりみち日和へようこそ」＋カテゴリ選択 → 初期設定では17:00〜21:00に1日1回の通知 → 実施記録または次へ送って後から戻す、という1周の案内。ジャンルなどの詳細設定は提案を見てから絞り込めることを予告＋「はじめる」
2. 興味カテゴリ選択：選択数が提案の幅に影響し、後から変更できることを案内。FilterChip 複数選択。0 件のときは「次へ」を無効化。詳細設定はここでは尋ねず、全候補から開始して、後から提案設定画面で調整
3. 通知許可画面：初期設定の時間帯・1日1回・後から変更可能であることを案内。「通知を許可する」／「あとで」。拒否しても手動提案だけで利用できる

個別機能の操作方法は、そのUIへ到達する前のオンボーディングでは説明しない。

### 通知

- 設定した通知時間帯（デフォルト 17:00〜21:00）の範囲内で、毎日 1 回ランダムな時刻にローカル通知を表示する（開始 == 終了は固定時刻）
- 単発通知を 7 日分先行予約し、アプリ起動時に張り直す（7 日以上未起動だと通知は止まり、次回起動で再開）。同じ日に 2 回は通知しない
- **文言は時間（分数）を名指ししない柔らかい誘い**：例「暇な時間って存在しますか？」「ちょっとした空き時間、ありませんか？」
- 通知本文タップ → **提案画面**（保存済みのカテゴリ＋詳細設定で提案）
- **通知の時間アクション（15/30/60分）は廃止**

### 提案完了モーダル

- 「おつかれさまです」「今回のよりみちはどうでしたか？」
- ChoiceChip 3 択：😊 よかった / 🙂 普通 / 😐 合わなかった
- 「これで完了」→ status = done ＋フィードバックを記録し、成功時は「記録しました」と表示

## 操作と記録

| 操作 | 動作 |
|---|---|
| やってみる | 完了モーダルを表示 → フィードバック選択 → `status = done` で履歴に保存 |
| スキップして次の提案 | 表示中の提案を `status = skipped` として記録し、同条件で再抽選して次を表示 |

注：企画書の処理フローには当初「やってみる / 別の提案 / スキップ」の 3 操作がありましたが、プロトタイプの提案カードはボタン 2 つです。本仕様では「スキップして次の提案」を押した時点で表示中の提案をスキップ記録とすることで両者を統合しています。

## データ設計

### `assets/data/suggestions/<category>.json`

提案候補は `music.json` / `cook.json` / `read.json` / `movie.json` / `walk.json` にカテゴリ単位で分割する。ファイル名は各レコードの `category` id と一致させ、`SuggestionRepository` が全ファイルを読み込んで従来と同じ `List<Suggestion>` に結合する。新カテゴリを追加するときは、カテゴリJSONと `suggestionAssetPathsByCategory` を同時に追加する。

| フィールド | 型 | 説明 |
|---|---|---|
| `id` | string | 提案 ID |
| `title` | string | 提案タイトル（カードの大見出し） |
| `description` | string | カードに表示する短い説明文 |
| `recipe` | string（料理のみ） | 料理（`cook`）の提案だけが持つレシピ本文。「詳しく見る」から展開する。材料の目安と 2〜4 ステップの手順を、「材料：」「手順：」・番号ごとの改行で読みやすく整形する。発展版では Claude API で動的生成する対象 |
| `category` | string | 主カテゴリ id（`music` / `cook` / `read` / `movie` / `walk`） |
| `tags` | string[] | **詳細設定の選択肢に対応する値**の配列（絞り込みに使う）。補助的な説明タグも許容するが、所属カテゴリの各詳細設定グループに一致するタグを必ず含める |
| `where_to_try` | string | 入手先・実践先の案内。全カテゴリ共通の必須フィールド |
| `estimated_minutes` | number | 目安所要時間（分）。履歴の合計時間集計に使う |
| `weight` | number | 重み付きランダム選択の重み |

旧スキーマから：`min_minutes`/`max_minutes` → `estimated_minutes` に統合。`intensity`（難易度）・`location_type`（移動距離）は**廃止**。`tags` は詳細設定の選択肢に対応する値の配列に役割変更。`detail` は料理専用の `recipe` に置き換え、`budget_yen`（予算）は**廃止**。`where_to_try`（入手先）は Issue #112 でいったん廃止したが、Issue #114 で全カテゴリ共通フィールドとして復活。

データ変更後は `flutter test test/repositories/suggestion_repository_test.dart` を実行し、各ファイルのJSON・必須項目・category一致・タグ整合と、全ファイル横断のID一意性を確認する。

### `records`（実施・スキップ履歴）

| フィールド | 型 | 説明 |
|---|---|---|
| `id` | string | 履歴 ID |
| `suggestion_id` | string | 提案 ID |
| `suggestion_title` | string | 提案タイトル |
| `category` | string | カテゴリ id |
| `estimated_minutes` | number | 集計に使う分数（表示した提案の `estimated_minutes`） |
| `status` | string | `done` または `skipped` |
| `feedback` | string \| null | `good` / `normal` / `bad`。skipped のときは null |
| `created_at` | string | 記録日時。ISO8601 |

### `user_settings`

| フィールド | 型 | 説明 |
|---|---|---|
| `selected_categories` | string[] | 選択中の興味カテゴリ id |
| `detail_settings` | Map<string, Map<string, string[]>> | カテゴリ id → グループ id → 選択値の配列 |
| `notification_enabled` | boolean | 通知 ON/OFF |
| `notification_start_time` | string | 通知時間帯の開始時刻。デフォルト `17:00` |
| `notification_end_time` | string | 通知時間帯の終了時刻。デフォルト `21:00`（旧 `notification_time` は開始＝終了として移行） |
| `theme_mode` | string | 表示テーマ。`system` / `light` / `dark`。デフォルト `light` |
| `first_launch_completed` | boolean | オンボーディング完了フラグ |
| `recent_suggestion_ids` | string[] | 直近重複除外用。直近 3 件 |

旧スキーマから：共通条件の `selected_minutes` / `budget_option` / `distance_option` を**廃止**し、カテゴリ別の `detail_settings` に統合。

## 提案ロジック

| 条件 | 判定 |
|---|---|
| カテゴリ | `suggestion.category` が `selected_categories` のいずれかと一致 |
| 詳細設定（タグ） | 選択済みグループの値が `suggestion.tags` に含まれる（グループ内 OR・グループ間 AND）。未選択グループは絞り込まない。絞り込みはタグ照合のみ（予算上限判定は廃止） |
| 直近重複 | `recent_suggestion_ids`（直近 3 件）に含まれる提案は除外 |
| 選択 | 候補から `weight` を考慮してランダムに 1 件選ぶ |

処理の流れ：

1. オンボーディングで興味カテゴリを登録する
2. 提案設定で未選択の詳細設定グループは指定なしとして扱う
3. カテゴリ別の提案JSONをすべて読み込み、1つの候補リストに結合する
4. 上記条件で候補を抽出し、直近 3 件を除外する
5. 候補があれば weight 付きランダムで 1 件選び、提案画面に表示する。表示した ID を `recent_suggestion_ids` に追加する
6. 候補がなければ、直近除外を一時解除して再検索する（同一提案の連続表示は避ける）
7. それでも候補がなければ、条件の変更（カテゴリを増やす・詳細設定を緩める）を促すメッセージを表示する
8. JSON 読み込みに失敗したら「データの読み込みに失敗しました。再起動してください。」と表示する

## 保存方式

| データ | 保存先 |
|---|---|
| 提案候補 | `assets/data/suggestions/<category>.json`（カテゴリ別・アプリ同梱） |

## 発展機能

MVP 完成後に、以下を検討します。

### 発展 Phase 1

- 提案候補の増加（各詳細設定の選択肢につき 50 件以上、MVP 全選択肢で対応済み）、カテゴリ追加（散歩・運動・芸術など、固有の詳細設定とともに。散歩は定義・データを先行整備済み）
- **詳細設定の複数項目化**（音楽＝言語・気分、料理＝栄養素・ダイエット、読書＝読書時間・入手予算、映画＝上映時間・視聴先。ジャンル 1 種類から拡張）
- **Claude API による料理レシピ（`recipe`）の動的生成**（カテゴリ・タイトル・タグを渡して生成。API キーはアプリ内に置かず Cloud Functions 側で管理）
- 実施率表示（履歴の今週 / 全期間・ステータスフィルターは実装済み）

### 発展 Phase 2

- iOS 版の platform ファイル生成、ビルド、実機確認
- iOS の通知許可、ローカル通知対応

### 発展 Phase 3

- Firebase Authentication（Google アカウント連携。設定画面の「連携」を有効化）
- Cloud Firestore による履歴・設定のクラウド保存（バックアップ）
- Cloud Functions for Firebase（AI API を安全に呼ぶ）

### 将来構想

- Google Calendar 連携、予定間の空き時間自動検出
- 位置情報を使った周辺スポット提案
- YouTube API・音楽サービス連携

AI 提案を導入する場合も、通知時に毎回 AI を呼ぶのではなく、提案候補をまとめて生成して保存し、通知時は保存済み候補からランダムに表示します。

## 実装上の注意

- MVP では外部 API・ログイン・個人情報を扱わない
- 提案設定は二段階方式（カテゴリ → カテゴリ別詳細設定）。MVP は各カテゴリ「ジャンル」1 グループのみ。難易度・移動距離・共通の使える時間は持たない
- 通知文言に分数を入れない。通知は「開くきっかけ」に徹し、提案は保存済み条件で行う
- 通知権限を拒否されても手動提案だけで利用できるようにする
- 通知の挙動は Android Emulator と Android 実機で確認する（iOS は発展版）
- まずは「オンボーディング」「提案表示」「履歴保存」をアプリ内で完結させ、通知は最後に組み込む
- UI プロトタイプ（React）はデザイン参照専用。提案設定画面は旧モデルのため要更新。React のコードや依存を Flutter 実装に持ち込まない
