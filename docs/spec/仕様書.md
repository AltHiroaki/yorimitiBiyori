## 1. 概要

### 1.1 アプリ名

よりみち日和

### 1.2 コンセプト

- 企画コンセプト：「好きなことで、いつもと違う角度から。」
- アプリ内タグライン：「空いた時間に、小さなよりみちを。」
- 差別化の核心（企画書 06）：「好きな領域の中で、知らなかった自分の好みと出会える」

ユーザーが興味カテゴリ（音楽・料理・読書・映画など）を選び、続けてそのカテゴリ固有の**簡単な詳細設定**で好みを絞り込むと、その条件に合う小さな「よりみち」行動を、内容（説明）つきでランダムに 1 件提案する（料理はレシピも添える）。これにより「浅く広い」提案ではなく、ライト層にとってちょうどよい具体性を持った提案を実現する。MVP では制作コストを現実的な範囲に抑えるため、詳細設定は各カテゴリ「ジャンル」など**1 種類のみ**に絞り、複数項目での絞り込みは発展機能として段階的に追加する（企画書 ver6 04）。

### 1.3 目的

空き時間があっても、何をするかを考えるには手間がかかり、いつも同じアプリ・同じ行動に流れてしまう（体験の固定化）。よりみち日和は、検索・比較・決定の工程をアプリが肩代わりし、短い空き時間に「好きなことの中の、いつもと少し違う一歩」を差し込むことを目的とする。

企画書 02 で整理した解決すべき課題は次の 3 点である。

| 課題 | 内容 |
|---|---|
| 体験の固定化 | 好きでもいつも同じものを選んでしまう。固定化した行動パターンから抜け出すきっかけがない |
| 「新しいもの」への踏み出しコスト | 違うものも試したいが、何を選べばよいかわからない。調べて選ぶ工程が面倒で結局同じになる |
| 詳細情報がないと試せない | 「ボサノバを」「タジンを」と言われても、どんなものかわからないと試す気になれない |

### 1.4 対象ユーザー

| 区分 | 内容 |
|---|---|
| 主要ターゲット | 音楽・料理・読書・映画などに「興味はあるが深掘りまではしない」**ライト層**の大学生・社会人 |
| 利用状況 | 待ち時間・移動時間などの「すきま時間」に、好きな領域の中から手軽に試せる提案を受ける |
| 利用動機 | 新しい体験への関心はあるが、自分で検索・比較・決定するほどの強い動機はない |
| 二次ターゲット | 趣味を広げたい人、何かを始めたいが何を選べばよいかわからない人 |

ターゲットを「ライト層」に絞るのは、マニア層は自力で深掘りできるためアプリの浅い提案では物足りず、逆に詳細情報の伴わない浅い提案ではライト層も動けないからである。**カテゴリ選択後の詳細設定**という二段階により、ライト層にとってちょうどよい粒度の提案を届ける。

### 1.5 対象プラットフォーム

| 項目 | 内容 |
|---|---|
| 種別 | Flutter によるスマートフォンアプリ |
| 対応端末 | MVP では Android を主な検証対象とする。iOS は発展版で検証する |
| 利用形態 | 初期実装版はログイン不要。ユーザー情報は端末内に保存する |
| 通知 | 端末のローカル通知を使用する。サーバーからのプッシュ通知は MVP に含めない |

### 1.6 MVP の定義

授業内で確実に完成させる最小構成を「初期実装版（MVP）」と定義する。中心機能「**カテゴリ選択 → 詳細設定 → 提案 → 履歴保存**」をまず安定させる方針とする。

| 区分 | 実装対象 | 扱い |
|---|---|---|
| 初期実装版（MVP） | Flutter、Dart、Material 3、カテゴリ別提案JSON、shared_preferences、flutter_local_notifications。カテゴリは音楽・料理・読書・映画の 4 種類、詳細設定は各カテゴリ「ジャンル」1 種類を基本とする（料理のみ「調理法」を追加した 2 種類） | 授業内で完成させる範囲。ログイン、外部 API、クラウド DB は入れない |
| 発展 Phase 1 | 提案候補の増加（各詳細設定の選択肢につき 50 件以上、MVP 全選択肢で対応済み）、Claude API による detail 動的生成 | 提案体験を改善する |
| 発展 Phase 1 | 詳細設定の複数項目化（音楽＝言語・気分、料理＝栄養素・ダイエット、読書＝読書時間・入手予算、映画＝上映時間・視聴先） | ジャンル 1 種類から、複数項目での絞り込みへ拡張する。料理の「調理法」グループは MVP で先行実装済み |
| 発展 Phase 1 | カテゴリの追加（散歩・運動・芸術など） | MVP コアの 4 カテゴリに、固有の詳細設定を持つカテゴリを追加する。散歩は定義・提案データを先行整備済み |
| 発展 Phase 2 | iOS platform 生成、iOS 通知確認、TestFlight | iOS 対応 |
| 発展 Phase 3 | Firebase Authentication、Cloud Firestore、Cloud Functions | ユーザー識別とクラウド保存。最初は匿名認証でもよい |
| 将来構想 | Google Calendar API、位置情報、Maps / Places API、YouTube・音楽サービス連携 | 必要性が確認できた段階で検討する |

## 2. 要件定義

### 2.1 機能要件：初期実装版（MVP）

| 機能 | 説明 | 優先度 |
|---|---|---|
| オンボーディング | 初回起動時に、ようこそ画面 → 興味カテゴリ選択 → 通知許可の 3 ステップを全画面で表示する。2 ステップ目以降は前へ戻れる | 必須 |
| 興味カテゴリ登録 | 音楽 / 料理 / 読書 / 映画 のカテゴリから複数選択する（散歩などは発展で追加） | 必須 |
| カテゴリ別詳細設定 | 選択した各カテゴリについて、そのカテゴリ固有の詳細設定を設定・保存する。MVP では各カテゴリ「ジャンル」**1 種類を基本**とする（料理のみ「調理法」を加えた2種類）。各項目は「指定なし」を許容する | 必須 |
| 提案表示 | カテゴリ＋詳細設定に合う提案を 1 件表示する | 必須 |
| 提案条件カード | 提案画面上部に現在の条件（選択カテゴリと有効な詳細設定）を表示する | 必須 |
| 提案カードの詳細情報 | 提案に「内容（説明）」と「入手先」を添えて、知らないものでも試せる状態にする。料理はさらにレシピ（recipe）を「詳しく見る」から展開できる | 必須 |
| 再提案 | 「スキップして次の提案」で同条件のまま別候補を表示する。表示中だった提案はスキップとして記録する | 必須 |
| 実施記録 | 「やってみる」→ 完了モーダルでフィードバック（よかった / 普通 / 合わなかった）を選び、実施済みとして記録する | 必須 |
| 履歴表示 | 実施数・スキップ数・合計時間と、履歴一覧を表示する。0 件時は空状態を表示する | 必須 |
| 履歴削除 | 設定画面から端末内の履歴を確認付きで削除できる | 必須 |
| 通知時間帯設定 | 通知の ON/OFF と通知時間帯（開始・終了、デフォルト 17:00〜21:00）を設定する | 必須 |
| ローカル通知表示 | 時間帯の範囲内で毎日 1 回、ランダムな時刻にローカル通知を表示する。文言は時間を名指ししない柔らかい誘い | 重要 |
| 通知からの起動 | 通知本文タップで提案画面を開く（保存済みのカテゴリ＋詳細設定で提案する） | 重要 |

### 2.2 MVP で実装しない機能

| 対象外機能 | MVP で入れない理由 |
|---|---|
| ユーザーログイン / Google アカウント連携 | アカウント設計・認証画面・データ移行が必要になり初期開発が重くなる。設定画面に「未連携」の行として置くのは可 |
| Firebase Authentication / Firestore | 発展機能として有効だが、MVP では端末内保存で価値検証できる |
| Claude API によるリアルタイム生成 | API キー管理、遅延、料金、失敗時処理が必要になる。MVP では JSON 候補から表示する |
| 通知の時間アクション（15/30/60分） | 時間を共通条件として扱わなくなったため廃止。通知は「開くきっかけ」に徹する |
| 詳細設定の複数項目化（言語・気分・栄養素・時間・予算・視聴先など） | 組み合わせの数だけ提案データが必要になり制作コストが膨大になる。MVP は各カテゴリ「ジャンル」1 種類に絞り、複数項目は発展 Phase 1 で追加する（企画書 ver6 04）。ただし料理の「調理法」グループは既存提案データ全件へのタグ付けで対応できたため MVP に先行実装した |
| 散歩などの追加カテゴリ | 企画書 ver6 の MVP コアは音楽・料理・読書・映画の 4 カテゴリ。散歩は定義・提案データを残しつつ、有効化は発展で行う |
| Google Calendar API | 趣味・条件選択型の MVP には必須ではない |
| 位置情報 / Maps / Places API | 権限取得と API 設計が増える。移動距離条件は廃止した |
| YouTube・音楽サービス連携 | 外部 API 連携は発展機能とする |
| PC ダッシュボード | スマートフォン体験を優先する |

### 2.3 非機能要件

| 項目 | 要件 |
|---|---|
| 操作性 | オンボーディングから提案表示までを短い操作で完了できる。主要操作は片手で押しやすいボタンにする |
| 応答性 | JSON 読み込み後の提案表示は即時に行う。通信待ちを発生させない |
| 保守性 | 画面、提案ロジック、保存処理、通知処理をファイル単位で分ける（`lib/src/` の構成は AGENTS.md を参照） |
| 拡張性 | カテゴリと詳細設定をマスター定義から駆動し、カテゴリ追加・詳細設定追加を後から行えるようにする。Firebase や Claude API も後から追加できるよう、提案データと履歴データのモデルを明確にする |
| 堅牢性 | 端末内保存の読み書きや JSON 解析に失敗しても画面が壊れないようにする |
| プライバシー | MVP ではログイン・位置情報・カレンダー情報を扱わない。端末内の履歴はユーザー操作で削除できる |

## 3. 画面仕様

配色は Material 3 のグリーン基調（primary `#3F6F44`、primaryContainer `#C2E8C0`、背景 `#F8FBF3`）。画面はボトムナビゲーション 3 タブ（提案 / 履歴 / 設定）構成。**ホーム画面は存在しない**（提案タブがトップ画面）。

> 画面構成・UI 文言・操作フローは UI プロトタイプ（`よりみち日和 UIプロトタイプ/`）を参考にするが、提案設定まわりは本仕様（二段階方式）が優先する。プロトタイプの `SuggestSettingsScreen.tsx` は旧モデル（時間/予算/移動距離）であり、**本仕様に合わせた更新が必要**である。

### 3.1 提案画面（タブ 1）

| 項目 | 内容 |
|---|---|
| ヘッダー | アプリ名「よりみち日和」＋タグライン「空いた時間に、小さなよりみちを。」 |
| 現在の提案条件カード | **全カテゴリ**を FilterChip で並べ、選択中のものだけを selected 表示にする。タップするとその場で選択が切り替わり、設定を保存して同じ画面で再抽選する（提案設定画面を開かずに絞り込みを変えられる）。ただし選択中が 1 件のときは解除させず、SnackBar「カテゴリは1つ以上選んでください」を表示する（3.4 の必須ルールと揃える）。右上に「◯つ選択中」。下部に有効な詳細設定の要約（例：ジャズ）と、提案設定画面へ移動する「変更 >」テキストボタン。詳細設定が未選択の場合は、未完了に見えないよう「詳細設定：すべてのジャンルから」と表示する |
| 今日のよりみちカード | ラベル「今日のよりみち」、提案タイトル（大見出し・2 行可）、説明文（description）、料理カテゴリのみ「詳しく見る」でレシピ（recipe）をカード内に展開、タグチップ、補助色の1行テキスト「目安 約N分」、続けて「入手先：〜」の1行テキスト（where_to_try）。所要時間は絞り込みタグではないため Chip に含めない。料理以外に展開 UI はない |
| アクション | 縦積みの2操作。「やってみる」は再生アイコン付きの全幅 FilledButton（高さ56・太字・影あり）、「スキップして次の提案」はスキップアイコン付きの全幅 TextButton（高さ48・影なし）。実施中カードも同じ階層で「完了」を主操作、「スキップ」を副操作にする |
| 案内カード | 「カテゴリは条件カードのチップをタップすると、その場で切り替わります。詳細設定は「変更」から調整できます。通知をタップすると、保存した条件のよりみちが表示されます。」 |
| 候補なし時 | 提案カードの代わりに、条件の変更（カテゴリを増やす・詳細設定を緩める）を促すメッセージを表示する |

「目安 約N分」の表示は共通の `SuggestionCardContent` を使う今日の提案・実施中・実施済み詳細・復活確認で統一する。履歴一覧では採用した時間の出所が分かるよう、日付・カテゴリと同じ文章行に「実測 N分」または「目安 N分」と表示し、両方は併記しない。

### 3.2 履歴画面（タブ 2）

| 項目 | 内容 |
|---|---|
| 見出し | 「履歴」＋「実施したよりみちと、スキップした提案を確認します。」 |
| 期間 | SegmentedButton で「今週 / 全期間」を単一選択。初期値は今週。今週は端末ローカル時刻の月曜日 00:00 から現在まで |
| サマリーカード | 3 分割：選択期間の実施数（緑）／スキップ数（黄）／合計時間・分。合計時間は期間内の done レコードごとに正常な実測時間を優先し、採用できない場合は `estimated_minutes` を使う。ステータスフィルタでは変えない |
| ステータス | FilterChip で「すべて / 実施 / スキップ」を単一選択。初期値はすべて |
| 履歴一覧 | 今週は「今週の履歴」、全期間は「最近の履歴」。各行：ステータスアイコン（✓ 緑＝実施、− 黄＝スキップ）、提案タイトル、日付、タグ・「実測 N分」または「目安 N分」、右端に実施/スキップバッジ。期間 → ステータスの順で絞り込み、新しい順 |
| 全体空状態 | サマリーは 0 表示のまま、「まだ履歴はありません」「よりみちを実行すると、ここに記録されます。」＋「提案を見てみる」ボタン（提案タブへ切替） |
| 絞り込み空状態 | 履歴はあるが結果が 0 件なら、「今週の履歴はありません」＋「全期間を見る」、または「この条件の履歴はありません」＋「すべて表示」 |

絞り込み状態は shared_preferences へ保存せず、HistoryPage の State が維持される間だけ保持する。完了フローから新しい `highlightedRecordId` を受け取った場合は、対象が表示される期間と「すべて」へ補正してから既存のハイライトを適用する。通常のタブ切替や履歴再読み込みでは選択を変えない。

実施率はプロトタイプに含まれないため、引き続き任意機能（発展 Phase 1）とする。

### 3.4 提案設定画面（サブ画面・二段階方式）

AppBar（戻るボタン＋タイトル「提案設定」）付きのサブ画面。提案画面の「提案設定」ボタンと設定画面の「提案設定」行の両方から遷移する。

二段階で構成する。

1. **第 1 段階：興味カテゴリ選択**（FilterChip・複数選択・絵文字付き）＋「◯つ選択中」。MVP は音楽・料理・読書・映画の 4 カテゴリ
2. **第 2 段階：選択した各カテゴリの詳細設定**。選択中のカテゴリごとにセクションを表示し、そのカテゴリの詳細設定グループを並べる。**MVP では各カテゴリのグループは「ジャンル」1 種類のみ**。各グループは FilterChip（複数選択）で、**未選択は「指定なし」＝そのグループでは絞り込まない**。

下部固定：「この条件で保存」（FilledButton）／「初期設定に戻す」（TextButton）。

初期表示：カテゴリの初期値は［音楽、読書、映画］。詳細設定はすべて未選択（指定なし）。ユーザーが詳細設定を選ばない限り、その項目では候補を絞り込まない。

#### カテゴリ（マスター定義）

MVP のコアカテゴリは音楽・料理・読書・映画の 4 種類。散歩は発展で追加するカテゴリ例として定義・提案データを残す（`InterestCategories.developmentCategories`）。

| id | 表示名 | 絵文字 | 区分 |
|---|---|---|---|
| music | 音楽 | 🎵 | MVP |
| cook | 料理 | 🍳 | MVP |
| read | 読書 | 📖 | MVP |
| movie | 映画 | 🎬 | MVP |
| walk | 散歩 | 🚶 | 発展（定義・データは先行整備済み） |

#### カテゴリ別の詳細設定（MVP・企画書 ver6 表3 準拠）

MVP では各カテゴリ「ジャンル」の 1 グループを基本とするが、料理のみ「調理法」グループを追加し、詳細設定の複数項目化を先行実装する。

| カテゴリ | グループ id | グループ名 | 選択肢 |
|---|---|---|---|
| 音楽 | genre | ジャンル | ポップス / ジャズ / クラシック / 洋楽 / ロック / ヒップホップ・R&B / アニソン・ゲーム音楽 / EDM・テクノ |
| 料理 | genre | 味覚・ジャンル | 和食 / 洋食 / 中華 / イタリアン / アジア風 / 激辛 / さっぱり / ガッツリ |
| 読書 | genre | ジャンル | エッセイ / 小説 / ノンフィクション / 詩集 / ミステリー・サスペンス / SF・ファンタジー / ビジネス・自己啓発 / 歴史・教養 |
| 映画 | genre | ジャンル | アクション / コメディ / ドラマ / SF / サスペンス / ファンタジー / 恋愛 / アニメ / ミステリー |
| （散歩・発展） | purpose | 目的 | 気分転換 / 運動 / 発見 |

> 映画の `tags` は 1 件の提案データに複数のジャンル値を持たせられる（例：`["アクション", "コメディ"]`）。実際の映画は複数ジャンルにまたがることが多いため、この形で表現する。
>
> 料理は「味覚・ジャンル」と「調理法」の2グループを持つため、グループ内 OR・グループ間 AND の絞り込みが実際に機能する最初のカテゴリになる。`assets/data/suggestions/cook.json` の料理データは全件が調理法タグを持つ（タグ漏れがあると、その調理法だけを選んだときに抽選が空になるため必須）。

#### 発展で追加する詳細設定（企画書 ver6 表3 の「発展版で追加」）

複数項目での絞り込みは発展 Phase 1 で追加する。

| カテゴリ | グループ id | グループ名 | 選択肢 |
|---|---|---|---|
| 音楽 | language | 言語 | 邦楽 / 洋楽 / 問わない |
| 音楽 | mood | 気分 | 作業向け / リラックス / 盛り上がりたい |
| 料理 | nutrition | 栄養素・ダイエット | 高タンパク / 低糖質 / 野菜多め / カロリー控えめ |
| 読書 | time | 読書時間 | 10分以内 / 30分 / じっくり |
| 読書 | budget | 入手・予算 | 電子書籍 / 〜500円 / 〜1000円 |
| 映画 | time | 上映時間 | 90分以内 / 問わない |
| 映画 | source | 視聴先 | Netflix / Amazon Prime / 問わない |

> 散歩の詳細設定は企画書に明記がないため本仕様で補完したものである。運動・芸術などのカテゴリも同じパターン（カテゴリ＋固有の詳細設定グループ）で発展的に追加できる。
>
> 「問わない」は明示的な「指定なし」と同義で、そのグループでは絞り込まない。

### 3.5 オンボーディング

初回起動時（`first_launch_completed == false`）のみ表示する。ステップ数は3つのまま維持し、全画面の上部に現在位置（「ステップ 1 / 3」〜「ステップ 3 / 3」）と3本のプログレスインジケーターを表示する。

3ステップとも全画面ページで表示し、モーダルは使わない。初回起動時は背後に表示すべき画面が存在せず、モーダルにしても「何かに重なっている」という意味を持たないためである。3画面とも「上部：戻る＋進捗／中央：スクロールする本文／下部：固定の操作ボタン」の同じ構造とし、ステップの切り替えは 250ms のフェードで行う。

2ステップ目以降は、画面左上の戻るボタンと端末の戻る操作で前のステップへ戻れる。戻ってもカテゴリの選択状態は保持する。1ステップ目には戻る先がないため戻るボタンを表示しない（進捗バーの位置がずれないよう領域だけ確保する）。

1. **ようこそ画面**：アイコン＋「よりみち日和へようこそ」＋「空いた時間に、小さなよりみちを。」。「好きなことを選ぶ」「空き時間にそっと届く」「やってみたら記録に残る」の3項目で、カテゴリ選択 → 初期設定では17:00〜21:00の間に1日1回の通知 → 実施記録または次へ送って後から戻す、という1周を案内する。「まずはこのまま。細かい好み（ジャンルなど）は、提案を見てから絞り込めます。」＋「はじめる」
2. **興味カテゴリ選択**：「興味のあるよりみちを選んでください」＋「選んだカテゴリの中から提案します。多めに選ぶほど、提案の幅が広がります。あとから変えられます。」。FilterChip 複数選択＋「◯つ選択中」。**0 件のときは「次へ」を無効化**。詳細設定はオンボーディングでは扱わず、初回はすべて「指定なし」で開始し、後から提案設定画面で調整する
3. **通知許可画面**：ベルアイコン＋「よりみちのきっかけを通知します」＋「初期設定では17:00〜21:00の間に、1日1回だけお知らせします。時間帯はあとから設定で変えられます。」＋「通知を許可する」／「あとで」

詳細設定を初回に尋ねると、カテゴリごとの多数の選択肢で開始までが長くなり、候補を早い段階で狭めて偶然の発見を減らす。そのため、オンボーディングではカテゴリだけを選び、まずは各カテゴリの全候補から提案する。ジャンルなどを絞れることはようこそ画面で予告し、実際の調整は提案を見た後に提案設定画面で行う。

「通知を許可する」で OS の通知権限をリクエストする。「あとで」または権限拒否でも、手動提案だけでアプリを利用できる。完了時に `first_launch_completed = true` を保存する。

オンボーディングではアプリの1周だけを説明する。「詳しく見る」、実施中カード、履歴画面での復活手順など、そのUIへ到達してから理解できる個別操作は説明に加えない。

### 3.6 提案完了モーダル

「やってみる」タップで表示する ModalBottomSheet。

| 項目 | 内容 |
|---|---|
| ヘッダー | チェックアイコン＋「おつかれさまです」＋「今回のよりみちはどうでしたか？」 |
| フィードバック | ChoiceChip 3 択：😊 よかった（good）/ 🙂 普通（normal）/ 😐 合わなかった（bad） |
| 保存 | 「これで完了」→ `status = done`＋feedback で records に保存し、モーダルを閉じて「記録しました」と表示する |

### 3.7 通知

通知は残すが、**時間（15/30/60分）を名指ししない柔らかい誘い文句**にする。通知は「アプリを開くきっかけ」に徹し、提案そのものは保存済みの条件（カテゴリ＋詳細設定）で行う。

| 項目 | 内容 |
|---|---|
| 通知時間帯 | `notification_start_time`〜`notification_end_time`（デフォルト 17:00〜21:00）の範囲内で、毎日 1 回ランダムな時刻（分単位・両端含む）に表示する。開始 == 終了は固定時刻通知として扱う |
| スケジュール方式 | 毎日リピート（`matchDateTimeComponents`）ではなく、**単発通知を 7 日分先行予約**する（通知 ID 4101〜4107）。アプリ起動時・設定変更時（`applySettings` 経由）に毎回張り直す |
| 同日重複の防止 | 予約したプランを端末に保存し（`5.4` 参照）、今日の予定時刻を過ぎていたら今日分は再予約しない（通知タップ→起動→再スケジュールで同じ日に 2 回通知しない）。未発火の予定は起動のたびに乱択し直してよい |
| 既知の制約 | 通知の発火時にアプリ側コードは動かないため、**7 日以上アプリを一度も開かないと通知は止まる**（次回起動時に再開）。端末再起動は BootReceiver が予約を復元する |
| 文言例 | タイトル「暇な時間って存在しますか？」本文「好きなことの中から、いつもと違うよりみちを提案します。」／「ちょっとした空き時間、ありませんか？」など。**具体的な分数は文面に入れない** |
| 本文タップ | アプリを起動し**提案画面**を開く。保存済みのカテゴリ＋詳細設定で提案する |
| 通知アクション | **設けない**（時間ボタン廃止）。タップで開くのみ |
| 通知 OFF | 設定の通知トグルが OFF のときは予約をすべてキャンセルし、保存済みプランも破棄する |

時間帯指定のランダム通知は、通知の偶然性（ふいの誘い）を出しつつ、深夜や授業中など不都合な時間の通知を避けるための方式である。完全ランダムは採用しない。1 日複数回の通知は行わない。

## 4. 画面遷移

### 4.1 通常起動時

```text
アプリ起動
├─ first_launch_completed == false → オンボーディング
│   ようこそ画面 → 興味カテゴリ選択 → 通知許可画面 → 提案画面（前のステップへは戻れる）
└─ first_launch_completed == true → 提案画面（タブ 1）

ボトムナビゲーション
├─ 提案（タブ 1）
├─ 履歴（タブ 2）
└─ 設定（タブ 3）

提案画面・設定画面 ─ 提案設定 → 提案設定画面（push）→ 保存 / 戻る → 元の画面
```

3 タブは横並びのページとして扱い、下タブのタップに加えて**横スワイプでも隣のタブへ移動できる**。下タブは 1 タップでどの目的地にも到達できることが前提のため、提案 ↔ 設定の直接移動は塞がない。代わりに、移動距離に応じてアニメーションを出し分ける。

| 操作 | 移動 | アニメーション |
|---|---|---|
| 横スワイプ | 隣接のみ（提案 ↔ 履歴 ↔ 設定） | 指の動きに追従（標準のページ送り） |
| タップ・隣接（±1） | 提案 ↔ 履歴、履歴 ↔ 設定 | 260ms のスライド。スワイプと同じ向きに動かす |
| タップ・飛び越し（±2） | 提案 ↔ 設定 | 中間の履歴ページを見せず、200ms のフェードで差し替える |
| 完了 → 履歴（自動遷移） | 提案 → 履歴 | 400ms。右から 0.12 ページ分のスライド＋フェードで、通常のタブ移動と区別する |

端末の「アニメーションを減らす」設定（`MediaQuery.disableAnimationsOf`）が有効なときは、いずれもアニメーションなしで即座に切り替える。

履歴の読み込みは**タブとしての表示が確定してから**行う。スワイプを始めた時点で隣のページも構築されるため、途中でやめた場合に不要な再読み込みが起きないようにする。

### 4.2 提案操作後の遷移

```text
提案画面
├─ やってみる → 実施中カードの「完了」→ 完了モーダルの「これで完了」（done + feedback）→ モーダルを閉じる
├─ スキップして次の提案 → 表示中の提案を skipped として記録 → 同条件で再抽選 → 提案画面を再表示
└─ 提案設定 → 提案設定画面（カテゴリ選択 → カテゴリ別詳細設定）
```

### 4.3 通知起動時

```text
設定した時間帯内のランダムな時刻にローカル通知を表示（時間を名指ししない文言）
└─ 通知本文をタップ → 提案画面（保存済みのカテゴリ＋詳細設定で提案）
```

通知から遷移した場合でも、提案ロジックはアプリ内の手動操作と同じ処理を使用する。通知は体験の入口であり、提案生成そのものは端末内の JSON 候補から行う。

## 5. データ設計

初期実装版（MVP）ではデータベースを用いない。提案候補データはアプリ内の JSON ファイルで管理し、設定・履歴は端末内（shared_preferences）に保存する。

### 5.1 提案候補データ：suggestions

企画書 08「行動カタログの設計」に準拠する。MVP 全カテゴリの各詳細設定選択肢につき、タグが一致する提案を 50 件以上収録する。

提案候補は `assets/data/suggestions/` 配下の `music.json` / `cook.json` / `read.json` / `movie.json` / `walk.json` にカテゴリ単位で分割する。ファイル名はレコードの `category` id と一致させる。`SuggestionRepository` は `suggestionAssetPathsByCategory` に定義した全ファイルを読み込み、1つの `List<Suggestion>` に結合する。新カテゴリ追加時はカテゴリJSONとパスマップを同時に更新する。

| フィールド | 型 | 説明 |
|---|---|---|
| `id` | string | 提案 ID。安定した一意な値（例：`music_jazz_focus`） |
| `title` | string | 提案タイトル（カードの大見出し） |
| `description` | string | カードに表示する短い説明文 |
| `recipe` | string（料理のみ） | 料理カテゴリ（`cook`）の提案だけが持つレシピ本文。提案カードの「詳しく見る」から展開する。材料の目安と 2〜4 ステップの手順を必須とし、「材料：」「手順：」を空行で分け、各手順を番号ごとに改行する（JSON では `\n` で保持）。発展版では Claude API で動的生成する対象 |
| `category` | string | 主カテゴリ。マスター定義のカテゴリ id（`music` / `cook` / `read` / `movie` / `walk`） |
| `tags` | string[] | **詳細設定の選択肢に対応する値**の配列（例：`["ジャズ", "作業向け", "無料"]`）。補助的な説明タグも許容するが、所属カテゴリの各詳細設定グループに一致するタグを必ず含める |
| `where_to_try` | string | 入手先・実践先の案内（例：「音楽配信アプリで「ジャズ」と検索して曲やプレイリストを探す。」）。全カテゴリ共通の必須フィールド |
| `estimated_minutes` | number | 目安所要時間（分）。履歴の合計時間集計と、時間系詳細設定の照合に使う |
| `weight` | number | 重み付きランダム選択の重み（基準 1.0） |

> 旧スキーマからの差分：`detail`（全カテゴリの詳細説明）は料理専用の `recipe` に置き換え、`budget_yen`（予算）は**廃止**した（予算の表示と予算絞り込みは行わない）。`where_to_try`（入手先）は Issue #112 でいったん廃止したが、Issue #114 で全カテゴリ共通フィールドとして復活させた。



### 5.2 実施履歴データ：records

| フィールド | 型 | 説明 |
|---|---|---|
| `id` | string | 履歴 ID |
| `suggestion_id` | string | 提案 ID |
| `suggestion_title` | string | 提案タイトル（提案データ更新後も履歴表示が壊れないよう非正規化して保持） |
| `category` | string | カテゴリ id |
| `estimated_minutes` | number | 実測時間を採用できない場合に使う目安分数。表示した提案の `estimated_minutes` を保持する |
| `status` | string | `done` / `skipped` |
| `feedback` | string \| null | `good` / `normal` / `bad`。skipped のときは null |
| `created_at` | string | 記録日時。ISO8601 形式 |
| `started_at` | string \| null | 実施開始日時。done は UTC の ISO8601、skipped と旧形式は null |
| `completed_at` | string \| null | 完了ボタンを押した日時。done は UTC の ISO8601、skipped と旧形式は null |

records の保存 JSON は `version: 2` と `records` 配列を持つ。version なしと version 1 は実測時刻なしとして後方互換で読み込み、レコードを維持する。version 2 の任意時刻が欠損・型不一致・パース不能でも、そのレコードは捨てず目安時間へフォールバックする。

### 5.3 ユーザー設定データ：user_settings

| フィールド | 型 | 説明 |
|---|---|---|
| `selected_categories` | string[] | 選択中の興味カテゴリ id（`music` など） |
| `detail_settings` | Map<string, Map<string, string[]>> | カテゴリ id → グループ id → 選択値の配列。MVP の例：`{"music": {"genre": ["ジャズ"]}}`。構造は複数グループ（発展）にも対応する。空・未設定は「指定なし」 |
| `notification_enabled` | boolean | 通知が有効かどうか |
| `notification_start_time` | string | 通知時間帯の開始時刻。デフォルト `17:00` |
| `notification_end_time` | string | 通知時間帯の終了時刻。デフォルト `21:00` |
| `first_launch_completed` | boolean | オンボーディング完了フラグ |
| `recent_suggestion_ids` | string[] | 直近重複除外用。直近 3 件の提案 ID |
| `theme_mode` | string | 表示テーマ。`system` / `light` / `dark`。デフォルト `light` |

> 旧スキーマからの差分：共通条件だった `selected_minutes` / `budget_option` / `distance_option` を**廃止**し、カテゴリ別の `detail_settings` に統合した。
>
> 通知時刻の移行：旧 `notification_time`（単一時刻）は読み込み時に**開始＝終了の縮退範囲**として引き継ぐ（従来の固定時刻動作を保存）。新キーが無効・開始 > 終了のときはデフォルト範囲へフォールバックする。保存時は新キーのみ書き出す。

### 5.4 保存先

| データ種別 | MVP の保存先 | 扱い |
|---|---|---|
| 提案候補 | `assets/data/suggestions/<category>.json` | 個人情報を含まないカテゴリ別データとしてアプリに同梱する |
| ユーザー設定 | shared_preferences（キー `yorimichi_biyori_settings`） | 端末内に保存する。クラウド同期はしない |
| 実施・スキップ履歴 | shared_preferences（キー `yorimichi_biyori_records`、JSON 文字列） | 履歴削除機能で削除可能にする |
| 通知予約プラン | shared_preferences（キー `yorimichi_biyori_scheduled_notification_plan`、エポックミリ秒の JSON 配列） | スケジュール済み通知時刻の控え。同日 2 回目の通知を防ぐ判定に使う。通知 OFF で破棄する |
| 認証情報 | 保存しない | MVP ではログインを扱わない |
| 位置情報・カレンダー情報 | 取得しない | MVP では扱わない |

## 6. 提案ロジック仕様

### 6.1 基本条件

ユーザーの設定（カテゴリ＋カテゴリ別詳細設定）に対して、以下を**すべて**満たす提案を候補とする。

| 条件 | 判定 |
|---|---|
| カテゴリ | `suggestion.category` が `selected_categories` のいずれかと一致する |
| 詳細設定（タグ） | 一致したカテゴリの詳細設定について、**選択済みの各グループ**ごとに、そのグループの選択値のいずれかが `suggestion.tags` に含まれること。**未選択のグループ（指定なし／問わない）では絞り込まない**。グループ内は OR、グループ間は AND。絞り込みはタグ照合のみで行う（`budget_yen` の廃止に伴い予算上限判定は行わない） |
| 直近重複 | `recent_suggestion_ids`（直近 3 件）に含まれる提案は候補から除外する |
| 選択 | 候補が複数ある場合は `weight` を考慮してランダムに 1 件選ぶ |

絞り込みの単位は「カテゴリ＋そのカテゴリの詳細設定」である。複数カテゴリを選んでいる場合、各カテゴリは自分の詳細設定で判定され、いずれかのカテゴリの条件を満たす提案が候補に入る（カテゴリ間は OR、各カテゴリ内のグループは AND）。

### 6.2 提案処理の流れ

1. オンボーディングで興味カテゴリが登録済みであることを前提とする
2. 条件を確定する。提案設定で未選択の詳細設定グループは「指定なし」として扱い、その項目では候補を絞り込まない
3. カテゴリ別の提案JSONをすべて読み込み、1つの候補リストに結合する（アプリ起動時に 1 回で十分）
4. 6.1 の条件で候補を抽出する
5. 候補があれば weight 付きランダムで 1 件選び、提案画面に表示する
6. 表示した提案 ID を `recent_suggestion_ids` に追加する（3 件を超えたら古いものから削除）
7. 候補がなければ 6.3 へ

### 6.3 候補がない場合の処理

| 状況 | 対応 |
|---|---|
| 直近重複の除外で候補が尽きた | 直近除外を一時的に解除して再抽出する。ただし直前に表示した 1 件と同じ提案は選ばない |
| それでも候補がない | 提案カードの代わりに、条件変更を促すメッセージを表示する（カテゴリを増やす / 詳細設定を緩める）。**条件の自動緩和は行わない**（ユーザーの意図しない提案を防ぐため） |
| カテゴリ未選択 | 提案設定への導線付きで、カテゴリ設定を促す |
| JSON 読み込み失敗 | 「データの読み込みに失敗しました。再起動してください。」と表示する。アプリはクラッシュさせない |

### 6.4 記録処理

| 操作 | 保存内容 |
|---|---|
| 実施中カードの「完了」→ 完了モーダルの「これで完了」 | 「完了」を押した直後に `completed_at` を確定し、`status = done`、`feedback = good / normal / bad`、開始・完了時刻を records に保存する。`created_at` は `completed_at` と同じ値にする |
| スキップして次の提案 | 表示中だった提案を `status = skipped`、`feedback = null`、開始・完了時刻は null として records に保存し、同条件で再抽選する |

> 設計判断メモ：企画書の処理フローは当初「やってみる / 別の提案 / スキップ」の 3 操作だったが、UI プロトタイプの提案カードはボタン 2 つである。本仕様では「スキップして次の提案＝表示中の提案のスキップ記録＋再抽選」として統合する。Issue #127 では「やってみる」を主操作として際立たせるため縦積みを採用し、副操作の文言にもスキップされることを明示した。スキップを記録したくない場合の挙動変更は発展時に検討する。

### 6.5 履歴集計

| 指標 | 定義 |
|---|---|
| 実施数 | `status == done` のレコード数 |
| スキップ数 | `status == skipped` のレコード数 |
| 合計時間（分） | done レコードごとに 6.5 の実測判定を行い、採用した分数の合計 |

履歴画面では先に期間を抽出し、その期間内レコードを上表のサマリーへ渡す。今週は端末ローカル時刻の月曜日 00:00 以上かつ現在時刻以下の `created_at` とする。ステータスフィルタはサマリーの後に一覧だけへ適用する。期間・ステータス判定は UI から分離した純粋関数とし、週間集計でも同じ期間定義を再利用する。

実測時間は done で開始・完了時刻が両方あり、`completed_at > started_at`、かつ経過時間が `min(max(estimated_minutes × 3, 15分), 180分)` 以下の場合だけ採用する。日付またぎは許可する。秒単位の経過時間を最も近い整数分へ四捨五入し、1分未満は1分とする。それ以外は `estimated_minutes` へフォールバックする。完了モーダルの操作時間は実測へ含めない。

## 9. セキュリティ・プライバシー

MVP ではログイン、位置情報、カレンダー情報、外部 API を扱わない。端末内に保存するデータは、興味カテゴリ・カテゴリ別詳細設定・通知設定・実施/スキップ履歴に限定する。

| 項目 | 方針 |
|---|---|
| 個人情報 | MVP では氏名、メールアドレス、位置情報、カレンダー情報を取得しない |
| 通知権限 | 通知の目的を説明してから OS の権限許可を求める。拒否された場合は手動提案だけで利用できる |
| 端末内保存 | shared_preferences に保存する。履歴削除機能を用意し、削除は取り消せないことを明示する |
| AI API キー | MVP では AI API を使わない。発展版で使う場合も Cloud Functions 側で管理し、アプリ内に直接置かない |
| Firestore | 発展版で導入する場合は、ユーザーごとの読み書き制限を Security Rules で設定する |
| Calendar 情報 | MVP では取得しない。将来導入する場合も予定タイトル・説明文・参加者・場所は保存しない方針にする |

## 付録. 提案データ例

```json
{
  "id": "music_jazz_focus",
  "title": "作業用にジャズを1曲だけ流す",
  "description": "歌詞のないジャズを1曲、作業や勉強のBGMにしてみる。集中したいときに向いた軽いよりみちです。",
  "category": "music",
  "tags": ["ジャズ", "作業向け", "無料"],
  "where_to_try": "音楽配信アプリで「作業用 ジャズ」と検索してプレイリストを開く。",
  "estimated_minutes": 5,
  "weight": 1.2
}
```

この例は、カテゴリ `music` を選び、MVP の詳細設定「ジャンル＝ジャズ」を選んだときに候補となる（`tags` が選択値を含むため）。`tags` の「作業向け」「無料」は発展で追加する詳細設定（気分・費用）に対応する予備の値で、MVP の絞り込みでは使わない。

料理カテゴリの提案はこれに加えて `recipe` を持つ：
