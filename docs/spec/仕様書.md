## 1. 概要

### 1.1 アプリ名

よりみち日和

### 1.2 コンセプト

- 企画コンセプトコピー（企画書）：「好きなことで、いつもと違う角度から。」
- アプリ内タグライン（プロトタイプ）：「空いた時間に、小さなよりみちを。」

ユーザーが興味カテゴリと条件（使える時間・予算・移動距離）を設定すると、その条件に合う小さな「よりみち」行動をランダムに 1 件提案する。提案には「どんなものか」「どこから始めるとよいか」を添え、知らないものでも試す判断ができる状態にする。

### 1.3 目的

空き時間があっても、何をするかを考えるには手間がかかり、いつも同じアプリ・同じ行動に流れてしまう。よりみち日和は、検索・比較・決定の工程をアプリが肩代わりし、短い空き時間に「いつもと少し違う一歩」を差し込むことを目的とする。

### 1.4 対象ユーザー

| 区分 | 内容 |
|---|---|
| 主要ターゲット | 音楽、読書、散歩、カフェなど、すでに好きなことがある大学生・社会人 |
| 利用状況 | スマートフォンでアプリを開く。通知をきっかけに、15 分・30 分・60 分の空き時間に合う提案を受ける |
| 利用動機 | 新しい体験への関心はあるが、自分で検索・比較・決定するほどの強い動機はない |
| 二次ターゲット | 趣味を広げたい人、何かを始めたいが何を選べばよいかわからない人 |

### 1.5 対象プラットフォーム

| 項目 | 内容 |
|---|---|
| 種別 | Flutter によるスマートフォンアプリ |
| 対応端末 | MVP では Android を主な検証対象とする。iOS は発展版で検証する |
| 利用形態 | 初期実装版はログイン不要。ユーザー情報は端末内に保存する |
| 通知 | 端末のローカル通知を使用する。サーバーからのプッシュ通知は MVP に含めない |

### 1.6 MVP の定義

授業内で確実に完成させる最小構成を「初期実装版（MVP）」と定義する。MVP では、ユーザーがオンボーディングで興味カテゴリを登録し、通知または手動操作から条件を決め、条件に合う提案を表示・記録できる状態を完成条件とする。

| 区分 | 実装対象 | 扱い |
|---|---|---|
| 初期実装版（MVP） | Flutter、Dart、Material 3、suggestions.json、shared_preferences、flutter_local_notifications | 授業内で完成させる範囲。ログイン、外部 API、クラウド DB は入れない |
| 発展 Phase 1 | 提案候補の増加、Claude API による detail 動的生成 | 提案体験を改善する |
| 発展 Phase 1 | 通知時間帯のランダム化 | ユーザーが指定した時間帯の中で、毎日ランダムな時刻に通知する |
| 発展 Phase 2 | iOS platform 生成、iOS 通知確認、TestFlight | iOS 対応 |
| 発展 Phase 3 | Firebase Authentication、Cloud Firestore、Cloud Functions | ユーザー識別とクラウド保存。最初は匿名認証でもよい |
| 将来構想 | Google Calendar API、位置情報、Maps / Places API、YouTube・音楽サービス連携 | 必要性が確認できた段階で検討する |

## 2. 要件定義

### 2.1 機能要件：初期実装版（MVP）

| 機能 | 説明 | 優先度 |
|---|---|---|
| オンボーディング | 初回起動時に、初回起動モーダル → 興味カテゴリ選択 → 通知許可の 3 ステップを表示する | 必須 |
| 興味カテゴリ登録 | 散歩 / 音楽 / 読書 / 学習 / カフェ / 写真 / 整理 / 休憩 / 運動 / 買い物 の 10 種から複数選択する | 必須 |
| 提案条件設定 | 使える時間（5/15/30/60 分）、予算、移動距離を提案設定画面で設定・保存する | 必須 |
| 通知時刻設定 | 通知の ON/OFF と通知時刻（デフォルト 17:30）を設定する | 必須 |
| ローカル通知表示 | 設定時刻にローカル通知を表示する | 必須 |
| 通知アクション | 通知上に 15 分・30 分・60 分の選択肢を表示し、押された時間を一時条件として提案画面を開く | 重要 |
| 提案表示 | 条件（時間・予算・移動距離・カテゴリ）に合う提案を 1 件表示する | 必須 |
| 提案条件カード | 提案画面上部に現在の条件（時間・予算・距離・カテゴリ）を表示する | 必須 |
| 再提案 | 「別の提案」で同条件のまま別候補を表示する。表示中だった提案はスキップとして記録する | 必須 |
| 実施記録 | 「やってみる」→ 完了モーダルでフィードバック（よかった / 普通 / 合わなかった）を選び、実施済みとして記録する | 必須 |
| 履歴表示 | 実施数・スキップ数・合計時間と、履歴一覧を表示する。0 件時は空状態を表示する | 必須 |
| 履歴削除 | 設定画面から端末内の履歴を確認付きで削除できる | 必須 |

### 2.2 MVP で実装しない機能

| 対象外機能 | MVP で入れない理由 |
|---|---|
| ユーザーログイン / Google アカウント連携 | アカウント設計・認証画面・データ移行が必要になり初期開発が重くなる。設定画面に「未連携」の行として置くのは可 |
| Firebase Authentication / Firestore | 発展機能として有効だが、MVP では端末内保存で価値検証できる |
| Claude API によるリアルタイム生成 | API キー管理、遅延、料金、失敗時処理が必要になる。MVP では JSON 候補から表示する |
| 通知時間帯のランダム化 | 固定時刻通知が安定してから導入する。MVP ではデフォルト 17:30 の固定通知で検証する |
| Google Calendar API | 趣味・条件選択型の MVP には必須ではない |
| 位置情報 / Maps / Places API | 権限取得と API 設計が増える。移動距離は location_type の静的属性で代替する |
| YouTube・音楽サービス連携 | 外部 API 連携は発展機能とする |
| PC ダッシュボード | スマートフォン通知起点の体験を優先する |

### 2.3 非機能要件

| 項目 | 要件 |
|---|---|
| 操作性 | オンボーディングから提案表示までを短い操作で完了できる。主要操作は片手で押しやすいボタンにする |
| 応答性 | JSON 読み込み後の提案表示は即時に行う。通信待ちを発生させない |
| 保守性 | 画面、提案ロジック、保存処理、通知処理をファイル単位で分ける（`lib/src/` の構成は AGENTS.md を参照） |
| 拡張性 | Firebase や Claude API を後から追加できるよう、提案データと履歴データのモデルを明確にする |
| 堅牢性 | 端末内保存の読み書きや JSON 解析に失敗しても画面が壊れないようにする |
| プライバシー | MVP ではログイン・位置情報・カレンダー情報を扱わない。端末内の履歴はユーザー操作で削除できる |

## 3. 画面仕様

UI プロトタイプ（`よりみち日和 UIプロトタイプ/src/app/components/`）の 10 画面に対応する。配色は Material 3 のグリーン基調（primary `#3F6F44`、primaryContainer `#C2E8C0`、背景 `#F8FBF3`）。

画面はボトムナビゲーション 3 タブ（提案 / 履歴 / 設定）構成。**ホーム画面は存在しない**（提案タブがトップ画面）。

AppBar（戻るボタン＋タイトル「提案設定」）付きのサブ画面。提案画面の「提案設定」ボタンと設定画面の「提案設定」行の両方から遷移する。

### 3.5 オンボーディング｜プロトタイプ 05・06・07

初回起動時（`first_launch_completed == false`）のみ表示する。カテゴリ選択画面の上部に 3 ステップのプログレスインジケーターを表示する。

1. **初回起動モーダル**：アイコン＋「よりみち日和へようこそ」＋「空いた時間にできる、小さなよりみちを提案します。まずは気になるカテゴリを選んでみましょう。」＋「はじめる」
2. **興味カテゴリ選択**：「興味のあるよりみちを選んでください」。FilterChip 複数選択＋「◯つ選択中」。**0 件のときは「次へ」を無効化**
3. **通知許可モーダル**：ベルアイコン＋「よりみちのきっかけを通知します」＋「空き時間に、小さな行動の提案をお届けします。通知はあとから設定で変更できます。」＋「通知を許可する」／「あとで」

「通知を許可する」で OS の通知権限をリクエストする。「あとで」または権限拒否でも、手動提案だけでアプリを利用できる。完了時に `first_launch_completed = true` を保存する。

### 3.6 提案完了モーダル｜プロトタイプ 09

「やってみる」タップで表示する ModalBottomSheet。

| 項目 | 内容 |
|---|---|
| ヘッダー | チェックアイコン＋「おつかれさまです」＋「今回のよりみちはどうでしたか？」 |
| フィードバック | ChoiceChip 3 択：😊 よかった（good）/ 🙂 普通（normal）/ 😐 合わなかった（bad） |
| 保存 | 「履歴に保存」→ `status = done`＋feedback で records に保存し、モーダルを閉じる |

### 3.7 通知｜プロトタイプ 08

| 項目 | 内容 |
|---|---|
| 通知時刻 | `notification_time`（デフォルト 17:30）に毎日表示する |
| 文言例 | タイトル「15分だけ、少し歩いてみませんか？」本文「近くを散歩して気分転換しましょう」／「30分の空き時間、ありませんか？」など |
| 本文タップ | アプリを起動し**提案画面**を開く |
| 通知アクション | 「15分」「30分」「60分」の 3 つ。押された時間を一時条件として提案画面を開く |
| 制約 | 通知アクションに 5 分やその他の時間を追加しない（Android の表示数制約と挙動の単純化のため）。5 分はアプリ内のみの選択肢 |
| 一時条件 | 通知アクションで選んだ時間は、そのセッション限りの上書きとし、保存済みの提案設定を書き換えない |

発展版では、固定の通知時刻だけでなく、ユーザーが通知を受け取りたい時間帯を指定し、その範囲内で毎日 1 回ランダムに通知する方式を検討する。たとえば 17:00〜21:00 のように範囲を決めておけば、通知の偶然性を出しつつ、深夜や授業中など不都合な時間の通知を避けやすい。MVP では通知機能の安定を優先し、この機能は実装対象外とする。

## 4. 画面遷移

### 4.1 通常起動時

```text
アプリ起動
├─ first_launch_completed == false → オンボーディング
│   初回起動モーダル → 興味カテゴリ選択 → 通知許可モーダル → 提案画面
└─ first_launch_completed == true → 提案画面（タブ 1）

ボトムナビゲーション
├─ 提案（タブ 1）
├─ 履歴（タブ 2）
└─ 設定（タブ 3）

提案画面・設定画面 ─ 提案設定 → 提案設定画面（push）→ 保存 / 戻る → 元の画面
```

### 4.2 提案操作後の遷移

```text
提案画面
├─ やってみる → 完了モーダル → 履歴に保存（done + feedback）→ モーダルを閉じる
├─ 別の提案 → 表示中の提案を skipped として記録 → 同条件で再抽選 → 提案画面を再表示
└─ 提案設定 → 提案設定画面
```

### 4.3 通知起動時

```text
設定時刻にローカル通知を表示
├─ 通知本文をタップ → 提案画面（保存済み条件で提案）
├─ 15分を選択 → 提案画面（selected_minutes = 15 を一時条件に）
├─ 30分を選択 → 提案画面（selected_minutes = 30 を一時条件に）
└─ 60分を選択 → 提案画面（selected_minutes = 60 を一時条件に）
```

通知アクションから遷移した場合でも、提案ロジックはアプリ内の手動操作と同じ処理を使用する。通知は体験の入口であり、提案生成そのものは端末内の JSON 候補から行う。

## 5. データ設計

初期実装版（MVP）ではデータベースを用いない。提案候補データはアプリ内の JSON ファイルで管理し、設定・履歴は端末内（shared_preferences）に保存する。

### 5.1 提案候補データ：suggestions

企画書 08「行動カタログの設計」に準拠する。初期リリース時点で **50 件以上**登録する（現在 50 件・各カテゴリ 5 件）。

| フィールド | 型 | 説明 |
|---|---|---|
| `id` | string | 提案 ID。安定した一意な値（例：`walk_unknown_street_15`） |
| `title` | string | 提案タイトル（カードの大見出し） |
| `description` | string | カードに表示する短い説明文 |
| `detail` | string | 始め方・コツなどの詳細説明。発展版では Claude API で動的生成する対象 |
| `category` | string | 主カテゴリ。10 種のカテゴリ表示名のいずれか |
| `tags` | string[] | カードに表示するタグ。カテゴリ照合の補助にも使う |
| `min_minutes` | number | 実施に最低限必要な分数（正の数、`min_minutes <= max_minutes`） |
| `max_minutes` | number | かかっても収まる目安の分数 |
| `intensity` | string | `light` / `normal` / `active`。**MVP ではフィルタに使わない予約フィールド** |
| `location_type` | string | `spot`（その場）/ `walk5` / `walk15` / `far` |
| `budget_yen` | number | 費用目安。無料は 0 |
| `where_to_try` | string | 入手先・場所・最初の一歩のヒント |
| `weight` | number | 重み付きランダム選択の重み（基準 1.0） |

### 5.2 実施履歴データ：records

| フィールド | 型 | 説明 |
|---|---|---|
| `id` | string | 履歴 ID |
| `suggestion_id` | string | 提案 ID |
| `suggestion_title` | string | 提案タイトル（提案データ更新後も履歴表示が壊れないよう非正規化して保持） |
| `category` | string | カテゴリ |
| `selected_minutes` | number | 履歴集計に使う分数。時間条件が指定されている場合は選択時間、指定なしの場合は表示した提案の `max_minutes` |
| `status` | string | `done` / `skipped` |
| `feedback` | string \| null | `good` / `normal` / `bad`。skipped のときは null |
| `created_at` | string | 記録日時。ISO8601 形式 |

### 5.3 ユーザー設定データ：user_settings

| フィールド | 型 | 説明 |
|---|---|---|
| `selected_categories` | string[] | 選択中の興味カテゴリ id（`walk` など） |
| `selected_minutes` | number \| null | 使える時間。`null` は指定なし、指定ありの場合は 5 / 15 / 30 / 60 |
| `budget_option` | string | `free` / `under500` / `under1000` / `unlimited` |
| `distance_option` | string | `unspecified` / `spot` / `walk5` / `walk15` / `far` |
| `notification_enabled` | boolean | 通知が有効かどうか |
| `notification_time` | string | 通知時刻。デフォルト `17:30` |
| `first_launch_completed` | boolean | オンボーディング完了フラグ |
| `recent_suggestion_ids` | string[] | 直近重複除外用。直近 3 件の提案 ID |

### 5.4 保存先

| データ種別 | MVP の保存先 | 扱い |
|---|---|---|
| 提案候補 | `assets/data/suggestions.json` | 個人情報を含まない共通データとしてアプリに同梱する |
| ユーザー設定 | shared_preferences（キー `yorimiti_biyori_settings`） | 端末内に保存する。クラウド同期はしない |
| 実施・スキップ履歴 | shared_preferences（キー `yorimiti_biyori_records`、JSON 文字列） | 履歴削除機能で削除可能にする |
| 認証情報 | 保存しない | MVP ではログインを扱わない |
| 位置情報・カレンダー情報 | 取得しない | MVP では扱わない |

## 6. 提案ロジック仕様

### 6.1 基本条件

ユーザーの設定（または通知アクションの一時条件）に対して、以下を**すべて**満たす提案を候補とする。

| 条件 | 判定 |
|---|---|
| 時間 | `selected_minutes == null` の場合は絞り込まない。指定ありの場合は `suggestion.min_minutes <= selected_minutes` |
| 予算 | `budget_option == unlimited` の場合は絞り込まない。指定ありの場合は `suggestion.budget_yen <=` 予算上限（free=0 / under500=500 / under1000=1000） |
| 移動距離 | `distance_option == unspecified` の場合は絞り込まない。指定ありの場合は `suggestion.location_type` が選択範囲内。包含順：`spot ⊂ walk5 ⊂ walk15 ⊂ far`（例：walk15 選択時は spot / walk5 / walk15 が候補） |
| 興味カテゴリ | `suggestion.category` または `tags` が、選択カテゴリの表示名と 1 つ以上一致する |
| 直近重複 | `recent_suggestion_ids`（直近 3 件）に含まれる提案は候補から除外する |
| 選択 | 候補が複数ある場合は `weight` を考慮してランダムに 1 件選ぶ |

### 6.2 提案処理の流れ

1. オンボーディングで興味カテゴリが登録済みであることを前提とする
2. 条件を確定する。提案設定で未変更のプルダウンは「指定なし」として扱い、その条件では候補を絞り込まない。通知アクション経由の場合は時間のみ一時上書きし、他は保存済み設定を使う
3. `suggestions.json` を読み込む（アプリ起動時に 1 回で十分）
4. 6.1 の条件で候補を抽出する
5. 候補があれば weight 付きランダムで 1 件選び、提案画面に表示する
6. 表示した提案 ID を `recent_suggestion_ids` に追加する（3 件を超えたら古いものから削除）
7. 候補がなければ 6.3 へ

### 6.3 候補がない場合の処理

| 状況 | 対応 |
|---|---|
| 直近重複の除外で候補が尽きた | 直近除外を一時的に解除して再抽出する。ただし直前に表示した 1 件と同じ提案は選ばない |
| それでも候補がない | 提案カードの代わりに、条件変更を促すメッセージを表示する（時間を延ばす / カテゴリを増やす / 予算・距離を緩める）。**条件の自動緩和は行わない**（ユーザーの意図しない提案を防ぐため） |
| カテゴリ未選択 | 提案設定への導線付きで、カテゴリ設定を促す |
| JSON 読み込み失敗 | 「データの読み込みに失敗しました。再起動してください。」と表示する。アプリはクラッシュさせない |

### 6.4 記録処理

| 操作 | 保存内容 |
|---|---|
| やってみる → 履歴に保存 | `status = done`、`feedback = good / normal / bad` として records に保存する |
| 別の提案 | 表示中だった提案を `status = skipped`、`feedback = null` として records に保存し、同条件で再抽選する |

> 設計判断メモ：企画書の処理フローは「やってみた / 別の提案 / スキップ」の 3 操作だが、UI プロトタイプの提案カードはボタン 2 つである。本仕様では「別の提案＝表示中の提案のスキップ記録＋再抽選」として統合した。スキップを記録したくない場合の挙動変更は発展時に検討する。

### 6.5 履歴集計

| 指標 | 定義 |
|---|---|
| 実施数 | `status == done` のレコード数 |
| スキップ数 | `status == skipped` のレコード数 |
| 合計時間（分） | done レコードの `selected_minutes` の合計 |

## 7. API・保存方式

### 7.1 初期実装版（MVP）

| 項目 | 内容 |
|---|---|
| 提案データ取得 | `assets/data/suggestions.json` をアプリ内から読み込む |
| 設定保存 | shared_preferences に保存する |
| 履歴保存 | shared_preferences に JSON 文字列として保存する |
| サーバー通信 | 行わない |
| ログイン | 不要 |
| 外部 API | 使用しない |

### 7.2 発展版の段階的な API・保存方式

| 段階 | 方式 | 内容 |
|---|---|---|
| 発展 Phase 1 | Claude API（Cloud Functions 経由） | 提案の `detail` を動的生成する。カテゴリ・タイトル・所要時間を渡し、毎回違う角度の説明を得る。API キーはアプリ内に置かない |
| 発展 Phase 1 | 通知時間帯ランダム化 | ユーザーが指定した通知時間帯の中で次回通知時刻をランダムに決め、通知後に次回分を再予約する |
| 発展 Phase 3 | Firebase Authentication | ユーザー識別。最初は匿名認証でもよい。Google ログイン（設定画面の連携行）は必要性が確認できてから |
| 発展 Phase 3 | Cloud Firestore | 興味カテゴリ・履歴・設定のクラウド保存（バックアップ） |
| 発展 Phase 3 | Cloud Functions for Firebase | AI API・外部 API を安全に呼ぶ |
| 将来構想 | Google Calendar API | 予定間の空き時間自動検出が必要になった場合に検討する |

AI 提案を導入する場合も、通知時に毎回 AI を呼ぶのではなく、候補をまとめて生成して保存し、通知時は保存済み候補からランダムに表示する。

## 9. セキュリティ・プライバシー

MVP ではログイン、位置情報、カレンダー情報、外部 API を扱わない。端末内に保存するデータは、興味カテゴリ・提案条件・通知設定・実施/スキップ履歴に限定する。

| 項目 | 方針 |
|---|---|
| 個人情報 | MVP では氏名、メールアドレス、位置情報、カレンダー情報を取得しない |
| 通知権限 | 通知の目的を説明してから OS の権限許可を求める。拒否された場合は手動提案だけで利用できる |
| 端末内保存 | shared_preferences に保存する。履歴削除機能を用意し、削除は取り消せないことを明示する |
| AI API キー | MVP では AI API を使わない。発展版で使う場合も Cloud Functions 側で管理し、アプリ内に直接置かない |
| Firestore | 発展版で導入する場合は、ユーザーごとの読み書き制限を Security Rules で設定する |
| Calendar 情報 | MVP では取得しない。将来導入する場合も予定タイトル・説明文・参加者・場所は保存しない方針にする |

## 付録. 提案データ例

```json
{
  "id": "walk_unknown_street_15",
  "title": "近くを15分だけ散歩する",
  "description": "スマホをしまって、いつも通らない道を少しだけ歩いてみる。気分転換に向いた軽いよりみちです。",
  "detail": "出発前に「今日は曲がったことのない角を1つ曲がる」と決めると、いつもの街でも小さな発見が増えます。",
  "category": "散歩",
  "tags": ["気分転換", "散歩"],
  "min_minutes": 10,
  "max_minutes": 15,
  "intensity": "light",
  "location_type": "walk5",
  "budget_yen": 0,
  "where_to_try": "自宅や学校の周りで、普段曲がらない角を1つ曲がってみる。",
  "weight": 1.2
}
```

実データは `assets/data/suggestions.json`（50 件・各カテゴリ 5 件）を参照。

以上
